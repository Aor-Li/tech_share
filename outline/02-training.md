## 章节契约

- 唯一目标：让听众能从一次训练更新的资源账本出发，看懂常用训练配置为什么存在，并按“先跑稳单卡/单副本，再解决容量，最后解决扩展效率”的顺序讨论方案。
- 预期结论：训练优化首先是工作负载与资源匹配问题；精度、batch/shape、重计算与并行策略都在交换计算、显存、通信或训练稳定性，必须在固定工作负载和目标下估算、观测并验证。
- 内容边界：训练 step 与 batch 体系、数据供给、Qwen/基础 dense LLM 的计算/理论时间/显存基线、step time 与吞吐、MFU/HFU、混合精度、attention kernel、重计算、DP、FSDP/ZeRO、TP 与序列切分，以及 H3 双向生成训练、causal 化改造训练和 rollout 训练的计算差异；不讲 H3 算法原理与效果、PP/EP 细节、组合并行、调度算法、通信公式或 profiler 教程。
- 输入：模型与数据形状、目标 global batch、精度、单卡容量、卡数/节点数、训练吞吐目标，以及 H3 三类训练经授权的执行图与调用次数。
- 输出：一次训练更新的计算/显存/通信账本、一条从简单基线到必要分片的选择路径、每项选择的收益与代价，以及可验证的初步瓶颈假设。
- 创作参考：`REF-001`、`REF-003`、`REF-004`、`REF-005`、`REF-006`。
- 事实依据需求：Qwen3-32B 规格使用 `FACT-002`，H3 同口径规模使用 `FACT-004`；模型演算、GPU 峰值、MFU/HFU 定义、并行算法、案例配置、吞吐、checkpoint 与集群数据在正文前登记核验；H3 详细训练流程另需经授权输入和对应事实记录，无法公开时使用变量化假设。

## 内容路径

### 2.1 拆开一次训练更新：数据如何进入，状态如何更新

- 按执行顺序说明 forward、backward 和 optimizer step 各自读取、保留或更新什么。
- 区分 micro-batch、gradient accumulation 和 global batch，说明它们如何组成一次 optimizer update；数据并行副本带来的扩展留到 2.4。
- 连接 batch/shape 与激活显存、计算粒度、吞吐和优化行为，避免把 global batch 只当吞吐参数。
- 数据同学可直接影响的部分包括样本长度/分辨率分布、padding、packing、预处理和数据加载是否让 GPU 等待。

### 2.2 用 Qwen/基础 dense LLM 建立训练资源基线

- 以一次 optimizer update 为统计口径，明确它覆盖的总样本/token 数、micro-step 数，以及总工作量与单设备分摊量。
- 沿用 01 的 GEMM/Attention 公式，按实际 forward、backward 和 update 调用次数完成“输入形状 → 单层 → 模型 → 一次训练更新”的 FLOPs 账本，不重新讲通用公式。
- 用对应精度的 GPU 峰值得到理论时间下界，再用 step time、samples/tokens per second、MFU/HFU 和完成时间解释训练效率；MFU 关注模型必要计算，HFU 还会受到重计算等实际硬件工作的影响。
- 建立参数、梯度、优化器状态、激活、临时空间、框架预留和通信 buffer 的显存账本，并用生命周期判断峰值。
- 默认使用 Qwen3-32B；如果具体机制受其专有设计干扰，则换用 Llama 等更基础的知名 dense decoder-only 模型或标准 Transformer 示意。

### 2.3 单卡/单副本先做四件常见的事

- 选择成熟的混合精度，在容量和速度收益之外明确数值稳定性边界。
- 调整 batch 和 shape，让计算有足够粒度，同时避免无效 padding。
- 使用成熟的 attention/kernel/fusion 能力；沿用 01 的“少搬数据、减少开销”直觉，只判断输入形状是否适用，不讲实现。
- Activation checkpointing 用额外计算换激活显存，展示计算、峰值显存和 step time 的前后对照账本。

### 2.4 多卡先从最容易理解的 DP 开始

- DP：每卡完整模型、处理不同数据，再同步梯度；用它补齐 global batch、吞吐扩展与 AllReduce 的关系。
- 如果完整训练状态放不下，再引出 ZeRO/FSDP：把优化器、梯度或参数分片，代价是需要更频繁聚合。
- 用相同模型和 global batch 的小例子比较复制与分片，区分总工作量、单卡工作量、通信和峰值显存，不展开 stage/API 差异。

### 2.5 模型或序列本身太大时再切模型

- TP：一层内部按张量维度切分，解决单层容量或算力问题，但通信更频繁。
- SP/CP：序列或上下文维度过大时切分，连接长序列和视频时空 token。
- PP：层数方向切分，会引入流水线空泡；EP：MoE 专家分布会引入路由和 AllToAll。二者只需形成识别能力。
- 不要求听众记忆所有正交维度乘积或设计大规模集群拓扑。

### 2.6 再比较 MiniMax H3 的三类训练计算

- 先复用 2.2 的同一资源账本列：工作单元、FLOPs/调用次数、可并行范围、峰值状态、通信和关键路径；不再从头解释计算、显存或通信概念。
- **双向生成训练**：按经授权的实际执行图，计算一次样本覆盖的时空 token、每次前向/反向的模块调用次数和 attention 可见范围带来的工作量；不展开生成目标本身。
- **causal 化改造训练**：只比较 causal 化前后 mask/窗口、可并行范围、状态复用和前向/反向调用次数如何改变总 FLOPs、峰值状态与关键路径。
- **rollout 训练**：把生成 rollout 与参数更新拆成两本账，分别统计采样条数、每条生成步数/窗口数、额外评估调用和更新 batch 的计算，避免只用一次训练 step 概括总成本。
- 三类训练统一使用变量化公式和同一输入假设，只回答“多算了什么、能否并行、要保留什么状态、总调用多少次”；不讲算法原理、效果或未经核验的 H3 规格。

### 2.7 训练侧收束：从现象到一次可验证改动

- 固定模型、数据、质量边界和目标指标，先用资源账本形成一个主要瓶颈假设，再选择一个杠杆验证。
- OOM 先定位峰值时存活的张量，再比较 batch/shape、精度、重计算或分片哪个最直接。
- GPU 利用率低先检查计算粒度、padding、数据供给和同步等待；多卡扩展差再检查每卡工作量、通信频率、跨节点映射和不可重叠尾部。
- 优化后更快但结果变化时，先确认精度、近似算法、工作负载或训练行为是否已经改变；不把不同条件下的数字直接比较。
