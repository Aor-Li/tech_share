## 章节契约

- 唯一目标：让听众看到模型、数据形状与硬件配置时，能估算计算和显存需求，并用执行效率、数据移动与通信解释“理论上需要多少”和“实际为什么更慢”。
- 预期结论：先定义工作单元，再依次估算 FLOPs、理论计算下界、峰值显存和必要的数据移动/通信；这些量级不能替代实测，但足以判断主要约束并读懂常用性能指标。
- 内容边界：GEMM/Attention 与模型级 FLOPs、Qwen3/MiniMax 案例、NVIDIA GPU 理论时间估计、MFU/HFU 基本口径、训练/推理显存账本、参数量估算、数据移动与 Roofline、可选 FlashAttention、GPU/节点层次与核心 collective；不讲逐算子穷举、GPU 微架构、Roofline 数学推导、通信算法与参数调优。
- 输入：模型结构、batch/序列/分辨率等数据形状、训练或推理阶段、精度与设备数量。
- 输出：计算量级、理想时间下界与利用率口径、主要显存项、可能的数据移动或通信约束，以及值得进一步观察的指标。
- 创作参考：`REF-001`、`REF-002`、`REF-003`、`REF-005`、`REF-006`；整体结构调研见 `references/research/ai-infra-content-architecture.md`。
- 事实依据需求：案例模型规格、NVIDIA GPU 各精度下的 dense 峰值/带宽、MFU/HFU 定义、训练与推理显存公式及任何具体性能数值在正文前登记核验；理论估计必须注明硬件、精度、dense/sparse 口径和工作单元。

## 内容路径

### 1.1 先定义工作单元和“快”

- 训练以一次 forward/backward/update 或一个 global batch 为工作单元；LLM 推理区分 prefill 和单步 decode；MiniMax H3 使用实际 step、窗口或流式输出单元。
- 训练关心 step time、samples/tokens per second 和完成时间；在线推理关心首包、单步/单帧延迟、吞吐和并发。
- batch、序列长度、分辨率、padding 和请求长度分布不是背景参数，而是资源消耗的第一输入。

### 1.2 计算需求：从 GEMM 和 Attention 到模型 FLOPs

- 先说明 FLOP、FLOPs 和 FLOP/s 的区别，统一乘加按 2 FLOPs 计的口径。
- 用 `[m,k] × [k,n] = 2mkn FLOPs` 解释 GEMM，再把 QKV/输出投影和 FFN 归入 GEMM 计算。
- 单独说明 Attention score 与 value 聚合如何随序列长度增长，建立线性投影项与序列二次项的形状直觉。
- 从单模块、单层汇总到模型，不逐算子穷举，也不先背脱离适用条件的模型级近似公式。

### 1.3 两个案例：同一方法，不同工作单元

- Qwen3-32B 选择一个训练或推理工作单元，较完整地展示“张量形状 → 模块 FLOPs → 单层 → 整体”的演算。
- MiniMax H3 使用同一套方法，突出时空 token、step 或窗口如何改变计算规模，不机械套用 LLM 的 token decode 公式。
- 案例输出同时给出计算量级和主要贡献项；如果 H3 细节不能公开，则保留变量化公式和经授权的输入假设。

### 1.4 从 FLOPs 到时间：理论下界与实际效率

- 使用 `理论计算下界 = FLOPs / 对应精度下的硬件峰值算力`，说明 NVIDIA GPU 峰值必须注明型号、精度和 dense/sparse 口径。
- 再解释形状太小、数据等待、串行依赖、同步以及 kernel/调度开销为什么让实际时间高于理论下界。
- 用 `粗略时间 ≈ FLOPs /（峰值算力 × 经验利用率）` 建立估算形式；经验利用率来自相似 workload 的实测，不给脱离条件的通用常数。
- MFU/HFU 用于解释训练效率：MFU关注模型必要计算相对峰值的利用，HFU还会受到重计算等实际硬件工作的影响；正文中给出严格定义和口径来源。
- 明确 MFU/HFU 不是在线推理的通用评价指标；推理仍需看延迟、吞吐、并发和 SLO。

### 1.5 显存容量：从参数量估算到峰值需求

- 训练分为参数、梯度、优化器状态、激活和临时空间；推理分为权重、临时状态，以及 LLM 的 KV cache 或 H3 自身运行状态。
- 参数量乘以相应格式的字节数，可以快速估算权重以及部分训练状态，但不能单独回答训练或推理是否放得下。
- 激活、KV/运行状态依赖 batch、序列长度、分辨率、层数和精度，必须从张量形状估算。
- 用生命周期时间线解释峰值显存由同时存活的张量决定，不是所有张量大小的机械相加；框架预留、workspace 和通信 buffer 作为额外项标注。

### 1.6 数据移动：容量够不等于算得快

- 用片上存储与 HBM 两层示意说明容量、访问速度和数据复用的差异，不进入 GPU 微架构。
- 算术强度连接“做多少计算”和“搬多少数据”；Roofline 只保留判断 compute-bound 与 bandwidth-bound 的图形直觉和理想下界。
- 明确数据移动包括张量的实际读写，不等同于静态显存占用。
- FlashAttention 作为可选深入案例：数学目标基本不变，通过 tiling 减少中间结果在 HBM 与片上存储之间往返；不展开 kernel 实现。

### 1.7 通信：多卡为什么不会自动更快

- 只建立卡内、本机卡间、跨节点三个层次，以及“越远通常越慢”的拓扑直觉。
- AllReduce 用于汇总，AllGather/ReduceScatter 用于把分片聚合或拆分；send/recv 用于相邻阶段。用张量前后变化讲，不推导 ring/tree 公式。
- 消息大小、调用频率和是否能与计算重叠，会共同决定通信是否暴露在关键路径上。
- AllToAll、PP/EP 的通信只点名，具体动机留到训练章或问答。

### 1.8 一张三问卡收束

面对一个 workload，先问：

1. 主要做多少计算，是否有足够并行度；
2. 峰值需要保留什么，主要反复搬什么；
3. 多设备之间交换什么、多久一次、是否卡住下一步。
