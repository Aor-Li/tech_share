## 章节契约

- 唯一目标：让听众看到算子和张量形状时，能建立计算、显存/数据移动和通信三本基础账，并理解理论下界为什么不等于实际时间。
- 预期结论：少量通用公式足以把张量形状转化为 FLOPs、搬运字节、驻留字节和通信量级；再结合硬件峰值、带宽、生命周期和拓扑，可以判断工作负载更可能受哪类资源约束，但不能替代具体工作负载中的实测。
- 内容边界：FLOP/FLOPs/FLOP/s、GEMM/Attention 与通用 block/模型级估算、参数量与 FLOPs 的条件化近似、数据移动与简化 Roofline、理论时间边界、通用显存组成与生命周期、GPU/节点层次与核心 collective；可用 Qwen3-32B 与 MiniMax H3 的参数量做一次 `2P`/`6P` 量级对照，不展开训练 step、prefill/decode、场景指标、完整训推显存账本或具体优化配置。
- 输入：算子或 block 结构、张量形状、数据精度、设备峰值/带宽和必要的设备拓扑。
- 输出：计算与数据移动量级、理想时间下界、同时驻留的主要张量、多设备带来的资源收益与通信代价，以及供 02、03 代入的统一估算方法。
- 创作参考：`REF-001`、`REF-002`、`REF-003`、`REF-005`、`REF-006`；整体结构调研见 `references/research/ai-infra-content-architecture.md`。
- 事实依据需求：NVIDIA GPU 各精度下的 dense 峰值与带宽、Qwen3-32B 与 H3-Omni-Transformer 的参数口径、任何具体硬件数值和演算结果在正文前登记核验；理论估计必须注明硬件、精度及 dense/sparse 口径。

## 内容路径

### 1.1 问题引入：一组张量运算需要多少资源和时间？

- 从“一组张量运算需要多少资源和时间”出发，把答案拆成计算、驻留/搬运和通信三本账。
- 说明答案取决于操作类型、张量形状、数据精度和硬件，不先引入具体模型或训推阶段。
- 提前区分量级估算与实测：前者用于排除不合理判断，后者用于确认真实关键路径。

### 1.2 计算工作量：从 GEMM 到参数量近似

- 在第一次估算前区分 FLOP、FLOPs 和 FLOP/s：FLOP 表示一次浮点运算，FLOPs 表示总工作量，FLOP/s 表示每秒处理能力；全篇统一将一次乘加计为 2 FLOPs。
- 从具体输入和权重的 shape 出发，用 `[m, k] × [k, n]` 和 `2mkn FLOPs` 解释 GEMM；说明标准 Transformer/DiT 的大部分 FLOPs 来自 GEMM，但不能由此断言实际时间一定由计算主导。
- 把 QKV/输出投影和 FFN 归入 GEMM 计算，再说明 Attention score 与 value 聚合如何随位置数量增长，建立投影项随位置数量线性增长、Attention 两次矩阵乘法随位置数量二次增长的形状直觉。
- 建立参数量与计算量的条件化近似：每个激活参数一次前向约 2 FLOPs，训练前向加反向约 6 FLOPs，推理前向与一次前向同口径；它只用于量级校验。两次 Attention 矩阵乘法、未激活参数、重计算和逐步生成的时间限制必须另算。
- 一次训练更新的调用次数留到 02，一次推理请求的 prefill/decode 口径留到 03；本章只给出带条件的 `2P` / `6P` 倍数，并用 Qwen3-32B 与 H3-Omni-Transformer 的参数量做一次量级代入，不展开场景工作单元。
- 只保留后续可重复代入的少量公式，不逐算子穷举。

### 1.3 数据移动：计算多不代表一定受算力限制

- 区分逻辑张量大小、同时驻留容量和执行期间的实际读写量：同一个张量可以只占一份容量，却被反复搬运多次。
- 用片上存储与 HBM 两层示意说明容量、访问速度和数据复用的差异，不进入 GPU 微架构。
- 用算术强度连接“做多少计算”和“搬多少数据”，再用简化 Roofline 建立 compute-bound 与 bandwidth-bound 的图形直觉和理想边界。
- 明确 Attention 的二次计算关系不等于实现时一定在 HBM 中完整物化 score 矩阵；tiling/IO-aware attention 只作为“数学目标近似不变、通过复用减少往返”的一句可选例子，具体 kernel 是否适用留到 02、03。

### 1.4 从工作量和数据量到理论时间边界

- 分别使用 `计算时间下界 = 总 FLOPs / 对应精度的峰值 FLOP/s` 和 `数据移动时间下界 = 搬运字节数 / 峰值带宽`，用两者中较慢的一侧形成单设备理想时间边界。
- 同一硬件在不同数据精度下的可用峰值和每元素字节数不同，因此必须注明 GPU 型号、数据精度以及 dense/sparse 口径。
- 再解释 shape 太小、并行度不足、同步、依赖以及 kernel/调度开销为什么让实际时间继续高于理想边界。
- 用 `粗略时间 ≈ 理论下界 / 相似工作负载的实测利用系数` 表达经验修正的形式；利用系数只能来自相似工作负载实测，不给通用常数，也不用于掩盖具体限制来源。
- 场景工作单元和训练/推理指标分别留到 02、03，本章不定义 step time、MFU/HFU、TTFT 或吞吐口径。

### 1.5 显存容量：大小之外还要看生命周期

- 用长期驻留张量、阶段性状态和临时空间建立通用显存分类，不在这里展开训练状态或推理 cache 的完整账本。
- 用 `张量容量 = num_elements × bytes_per_element` 估算单项容量，并再次区分静态占用与执行期间累计搬运量。
- 用简化生命周期时间线解释峰值显存不是所有张量大小的机械相加，并标注框架预留、workspace 和通信 buffer 等额外项。
- 训练中的参数/梯度/优化器/激活账本和推理中的权重/cache/运行状态账本分别留到 02、03。

### 1.6 多设备资源与通信代价

- 引入更多设备可以增加聚合计算资源和物理显存，但能否用于单个工作负载取决于复制或切分方式；通信是组织这些资源协同工作所付出的代价，多设备不会自动线性加速。
- 只建立复制更偏向增加总吞吐、切分可让单个工作负载使用聚合资源的直觉；具体 DP、FSDP、TP 和序列切分留到 02、03。
- 建立卡内、本机卡间、跨节点三个层次，以及“越远通常越慢”的拓扑直觉。
- AllReduce 用于汇总，AllGather/ReduceScatter 用于把分片聚合或拆分，send/recv 用于相邻阶段；用张量前后变化讲，不推导 ring/tree 公式。
- 用 `逻辑通信量 = 张量元素数 × 每元素字节数` 建立最小量级估算；消息大小、调用频率、路径和能否与计算重叠，共同决定通信是否暴露在关键路径上。
- 具体是哪种训练或推理配置产生这些通信，分别留到 02、03。

### 1.7 一张四问资源判断卡收束

面对任意工作负载，先问：

1. **算多少、搬多少**：主要 FLOPs 和数据流量是什么量级；
2. **理论最快多少**：当前 shape 更可能受峰值算力还是内存带宽限制；
3. **放得下吗**：峰值时哪些张量同时存活，还有哪些额外空间；
4. **单设备不够怎么办**：增加了哪些聚合资源，设备之间交换什么、多久一次、是否卡住下一步。

四问只用于形成量级判断和瓶颈假设，真实关键路径仍需在固定工作负载下实测。
