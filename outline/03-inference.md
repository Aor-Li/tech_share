## 章节契约

- 唯一目标：让听众能根据模型类型、输入分布和延迟/吞吐目标，理解常用推理优化分别在解决什么问题。
- 预期结论：推理优化必须先区分单请求与多请求、在线与离线，以及 LLM 和视频模型的执行方式；量化、batching、cache 和并行切分不是可以脱离目标独立比较的“加速开关”。
- 内容边界：LLM prefill/decode、H3/视频工作单元、量化、常用 kernel/编译能力、batching、KV/状态管理、复制与模型切分、基础评估；不讲调度算法、CUDA Graph 实现、框架参数大全和复杂分布式 serving 架构。
- 输入：模型类型、输入长度/分辨率/步数、请求分布、质量约束、SLO 与硬件资源。
- 输出：当前关键路径、候选优化、可能收益与质量/容量/复杂度代价。
- 创作参考：`REF-001`、`REF-002`、`REF-007`；整体结构调研见 `references/research/ai-infra-content-architecture.md`。
- 事实依据需求：KV cache、量化支持、speculative decoding、服务框架能力及任何性能数据在正文前登记核验。

## 内容路径

### 3.1 先把四种问题分开

- 在线更在意尾延迟和并发，离线更在意总吞吐和单位成本。
- LLM prefill 一次处理整段输入，decode 逐步生成；两者的并行度、数据读取和指标不同。
- MiniMax H3 / 视频模型按实际 step、分辨率、时空 token 或流式窗口分析，不强行使用 LLM KV cache 叙事。
- 输入长度和分辨率分布会同时改变单请求成本、batch 组成和尾延迟，是算法与数据侧的重要输入。

### 3.2 单次执行：少算、少搬或用更合适的格式

- 量化减少权重/状态占用和数据搬运，但必须同时说明质量、硬件与 kernel 支持。
- attention kernel、fusion、编译和图执行只归为“减少搬运或运行时开销”，用一个前后时间线建立直觉。
- LLM speculative decoding 作为“减少串行等待”的算法级例子，只讲机制与适用边界。
- H3 的步数、窗口、cache/复用或模型结构变化如果改变数学问题或质量，需要与纯系统优化分开。

### 3.3 多请求：显存空间会转化为并发能力

- 静态 batch 与 continuous batching 用排队示意讲清，不展开调度算法。
- LLM 用 KV cache 解释为什么请求长度分布、分页管理和 prefix 复用会影响可并发请求数。
- H3 使用自身的中间状态、流水阶段和复用机会，不与 LLM 做不成立的一一对应。
- 每项“显存节省”最终都要回答是否带来更大 batch、更多并发或更低延迟。

### 3.4 多卡：复制还是切分

- 请求级复制适合提高总吞吐和并发；模型切分用于单卡放不下或单请求目标无法满足。
- TP/PP 等名词沿用训练章，但推理更敏感于小 batch、同步和尾延迟，不能直接照搬训练配置。
- Prefill–decode 解耦和复杂分布式调度只作为完整版本末尾的“知道存在”，不进入方案细节。

### 3.5 评估时至少同时报告目标和代价

- LLM：TTFT、单步/每 token 延迟、端到端时延、吞吐、并发、显存和质量。
- H3：首帧/首段、每步或每帧时延、总吞吐、显存、稳定性和质量。
- 结果必须同时说明 workload、batch、精度和硬件；不展示脱离条件的加速倍数。
