## 章节契约

- 唯一目标：让听众能从一次推理请求的资源账本出发，根据模型类型、输入分布和延迟/吞吐目标，理解常用推理优化分别在解决什么问题。
- 预期结论：推理优化必须先区分单请求与多请求、在线与离线，以及 LLM 和视频模型的执行方式；量化、batching、cache 和并行切分不是脱离目标独立比较的“加速开关”，必须同时验证性能、容量和质量代价。
- 内容边界：Qwen/基础 dense LLM 的 prefill/decode 计算、理论时间、显存和指标基线，H3 双向视频生成、流式视频生成与 prompt 插入流程，量化、常用 kernel/编译能力、batching、KV/状态管理、复制与模型切分、基础评估；不讲 H3 算法语义与质量效果、调度算法、CUDA Graph 实现、框架参数大全、复杂分布式 serving 架构或 profiler 教程。
- 输入：模型类型、输入长度/分辨率/步数、请求分布、质量约束、SLO、精度、硬件资源，以及 H3 三类推理经授权的执行顺序与状态复用边界。
- 输出：单请求与多请求的计算/显存/关键路径账本、候选优化及其质量/容量/复杂度代价、H3 三类流程的同口径对照，以及可验证的初步瓶颈假设。
- 创作参考：`REF-001`、`REF-002`、`REF-005`、`REF-007`；整体结构调研见 `references/research/ai-infra-content-architecture.md`。
- 事实依据需求：Qwen3-32B 规格使用 `FACT-002`，H3 同口径规模使用 `FACT-004`；模型演算、GPU 峰值、KV cache、量化支持、speculative decoding、服务框架能力及任何性能数据在正文前登记核验；H3 详细推理流程另需经授权输入和对应事实记录，无法公开时使用变量化假设。

## 内容路径

### 3.1 先把四种问题和工作单元分开

- 用在线/离线 × LLM/H3 四象限先固定目标：在线更在意尾延迟和并发，离线更在意总吞吐、完成时间和单位成本。
- LLM 分别以一次 prefill、单步 decode 和完整生成作为估算单位；H3/视频模型按实际 step、分辨率、时空 token、流式窗口或完整生成分析。
- 输入长度、输出长度和分辨率分布会同时改变单请求成本、batch 组成、状态大小与尾延迟，是算法和数据侧的重要输入。
- 不把 LLM 的 token decode、KV cache 或每 token 指标机械套用到 H3。

### 3.2 用 Qwen/基础 dense LLM 建立推理资源基线

- 沿用 01 的 GEMM/Attention 公式，分别完成 prefill、单步 decode 和完整生成的“输入形状 → 单层 → 模型 → 请求”FLOPs 账本，不重新讲通用公式。
- 用对应精度的 GPU 峰值得到理论时间下界，再结合并行度、权重/状态读取和串行依赖解释 prefill 与 decode 为什么可能落在不同约束区域。
- 建立权重、KV cache、临时张量、框架预留和通信 buffer 的显存账本，说明输入长度、输出长度、batch 与并发如何改变峰值和可服务请求数。
- 统一报告 TTFT、单步/每 token 延迟、端到端时延、吞吐、并发、显存和质量，并注明 workload、batch、精度和硬件。
- 默认使用 Qwen3-32B；如果具体机制受其专有设计干扰，则换用更基础的知名 dense LLM 或标准 Transformer 示意。thinking/non-thinking 只在确实改变工作负载时出现。

### 3.3 再比较 MiniMax H3 的三类推理流程

- 复用 3.2 的同一资源账本列：工作单元、FLOPs/调用次数、可并行范围、峰值状态、可复用/需重算内容和关键路径；不从头解释计算或显存概念。
- **双向视频生成**：画出完整输入、迭代 step 与视频 token/latent 的更新顺序，统计每步处理范围、总 step 数、可并行部分、峰值状态和完整生成时间。
- **流式视频生成**：按首段与后续窗口拆开关键路径，标出每个窗口新增计算、可复用状态、窗口间依赖，以及首帧/首段时延和稳态每段成本。
- **prompt 插入流程**：标出 prompt 进入生成时间线的位置，以及插入前后哪些条件编码、视频状态或窗口需要新增、失效或重算；分别核算插入响应时延与后续生成成本。
- 三类流程只比较计算图、执行顺序、复用/重算、峰值状态和关键路径；算法语义、质量效果和未公开实现不进入本章。

### 3.4 单次执行：少算、少搬或用更合适的格式

- 量化减少权重/状态占用和数据搬运，但必须同时说明质量、硬件与 kernel 支持。
- attention kernel、fusion、编译和图执行沿用 01 的“少搬数据、减少运行时开销”直觉，用一个前后时间线判断收益来源和适用形状。
- LLM speculative decoding 作为“减少串行等待”的算法级例子，只讲机制与适用边界。
- H3 的步数、窗口、cache/复用或模型结构变化如果改变数学问题或质量，需要与纯系统优化分开。

### 3.5 多请求：显存空间会转化为并发能力

- 静态 batch 与 continuous batching 用排队示意讲清，不展开调度算法。
- LLM 用 KV cache 解释为什么请求长度分布、分页管理和 prefix 复用会影响可并发请求数。
- H3 使用自身的中间状态、流水阶段和复用机会，不与 LLM 做不成立的一一对应。
- 每项显存节省最终都要回答是否带来更大 batch、更多并发、更低延迟或更低单位成本。

### 3.6 多卡：复制还是切分

- 请求级复制适合提高总吞吐和并发；模型切分用于单卡放不下或单请求目标无法满足。
- TP/PP 等名词沿用训练章，但推理更敏感于小 batch、同步和尾延迟，不能直接照搬训练配置。
- Prefill–decode 解耦和复杂分布式调度只作为完整版本末尾的“知道存在”，不进入方案细节。

### 3.7 推理侧收束：同时报告目标、代价与验证结果

- 固定请求分布、质量边界、硬件和目标指标，先用资源账本形成一个关键路径假设，再只改变一个主要杠杆。
- 平均吞吐高但尾延迟差时，先检查请求长度/分辨率分布、排队、batch 组成和状态池压力。
- 优化后更快但输出变化时，先确认精度、近似算法、步数、窗口或工作负载是否已经改变。
- 结果必须同时报告目标指标、显存/并发变化、质量或稳定性代价和停止条件；不展示脱离条件的加速倍数。
