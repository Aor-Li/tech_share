# 03 第三章：推理——从单次执行到并发服务

## 章节契约

- 唯一目标：让听众从一次推理请求的执行阶段和资源账本出发，判断瓶颈来自计算、数据移动、串行依赖还是状态容量，并据此理解单请求、并发服务和多卡部署中的主要选择。
- 预期结论：推理优化不是罗列加速技术，而是先固定工作负载、质量边界和目标指标，再判断应该缩短单请求关键路径、提高请求复用效率，还是聚合更多设备；量化、batching、cache、复制和模型切分都必须回到账本与实测验证。
- 内容边界：以主流 dense decoder-only LLM 完整讲解 prefill/decode、计算与显存账本、指标、量化、常用 kernel/编译、speculative decoding、continuous batching、KV cache 管理、prefix reuse、复制与模型切分；视频/扩散类模型只用于说明工作单元、状态和质量边界不能照搬 LLM。需要具体形状、规格或工作负载时可用 Qwen3/MiniMax H3，但不按型号设置固定小节；不讲调度算法、CUDA Graph 实现、框架参数大全、复杂分布式 serving 架构或 profiler 教程。
- 输入：模型执行方式、输入/输出长度或分辨率/步数分布、请求到达分布、质量约束、SLO、精度和硬件资源，以及被选案例中已公开且经核验的执行顺序与状态复用边界。
- 输出：一次请求的计算/显存/关键路径账本、三类主要瓶颈假设、从单请求到并发和多卡的选择路径、每项候选优化的账本变化与代价，以及可复现的验证条件。
- 创作参考：`REF-001`、`REF-002`、`REF-005`、`REF-007`；整体结构调研见 `references/research/ai-infra-content-architecture.md`。
- 事实依据需求：模型演算、GPU 峰值、KV cache、量化支持、speculative decoding、continuous batching、paged KV、prefix reuse、chunked prefill、服务框架能力及任何性能数据在正文前登记核验；Qwen3/MiniMax H3 可使用已有事实作为普通实例，如展开型号差异，另需核验其相对主流模型的关键差异与策略价值，无法公开时不进入主讲。

## 内容路径

### 3.1 先定义“快”：工作单元、服务目标和比较条件

- 在线服务优先关注 TTFT、每 token/每步延迟、端到端时延、P95/P99 和稳定并发；离线任务优先关注总吞吐、完成时间和单位成本。
- 自回归 LLM 分别以一次 prefill、单步 decode 和完整生成作为估算单位；输入长度、输出长度和请求到达分布共同决定成本与服务压力。
- 视频/扩散类模型只用一张边界对照说明其工作单元可能是 denoising step、分辨率、时空 token、流式窗口或完整生成，不把 token decode、KV cache 和每 token 指标机械套用过去。
- 在比较任何方案前固定模型与质量边界、输入分布、输出上限、精度、batch/并发、硬件和服务目标，避免把不同问题下的结果放在一起。

### 3.2 拆解一次 LLM 请求：prefill、decode 与三本账

- 用一条时间线展示请求进入后依次经历 prefill 和多步 decode：prefill 可以同时处理输入位置，decode 具有逐 token 的串行依赖。
- 沿用 01 的 GEMM/Attention 方法，分别填写 prefill、单步 decode 和完整生成的计算账，只代入场景形状和调用次数，不重新推导通用公式。
- 建立权重、KV cache、临时张量、框架预留和通信 buffer 的显存账；说明 KV cache 随层数、KV head、精度、上下文长度、batch 和并发变化。
- 将计算下界、权重/KV 搬运、可并行粒度和串行依赖放进时间账，解释 prefill 与 decode 为什么容易落在不同约束区域，但不把“prefill 一定计算受限、decode 一定带宽受限”写成无条件结论。
- 默认使用无品牌 decoder-only Transformer；需要具体形状时可使用 Qwen3-32B 或其他资料完整的主流 dense LLM。

### 3.3 从账本定位瓶颈：工作量、数据移动还是状态容量

- 第一类问题是工作量或串行步骤过多：完整生成慢，即使单步已经充分利用硬件，也可能受输出长度和逐步依赖限制。
- 第二类问题是数据移动或运行时开销过大：每步计算粒度小、反复读取权重/KV，或大量小 kernel 使实际时间远高于计算下界。
- 第三类问题是状态容量过大：权重或 KV cache 挤占显存，限制 batch、可服务请求数和峰值流量承载能力。
- 用“现象 → 账本证据 → 关键路径假设”连接后续技术：单请求慢、多请求吞吐低和高负载尾延迟差不默认归因于同一瓶颈。

### 3.4 优化单请求：缩短当前关键路径

- **少搬、少存**：权重、激活或 KV 量化可以降低驻留和搬运字节，但必须同时说明质量、校准、硬件和 kernel 支持。
- **提高复用、减少运行时开销**：attention kernel、fusion、编译和图执行沿用 01 的 IO 直觉，用前后时间线说明减少了哪些搬运、kernel 启动或中间张量。
- **减少串行等待**：speculative decoding 作为算法级例子，说明草稿与验证如何减少必须串行执行的大模型步数，同时保留接受率、额外计算和输出一致性边界。
- 视频/扩散模型中的减少步数、窗口变化、cache/复用和结构变化只用于说明边界：如果改变了数学问题或输出质量，就不能与保持目标不变的系统优化混为一类。
- 每项方法统一回答四个问题：解决的瓶颈、改变的账本项、代价或副作用、适用工作负载。

### 3.5 从一次请求到持续服务：batch、状态池与尾延迟

- 用同一组长短请求对比静态 batching 与 continuous batching：后者可以在不同请求完成时补入新请求，但收益取决于请求分布和每轮可组合的工作。
- 用 KV cache 的动态增长解释连续物理空间、碎片和预留为何限制并发；paged KV 只讲分块管理如何提高状态池利用率，不展开分页实现。
- prefix reuse 用“共享相同前缀时少做什么、额外保留什么状态”说明计算与容量交换，并明确命中率和淘汰策略会影响实际收益。
- 用长 prefill 与正在进行的 decode 竞争执行资源解释平均吞吐与尾延迟可能冲突；chunked prefill 只作为拆分长工作、改善交错机会的直觉，不进入调度算法。
- 每项显存或调度改进最终都要回答是否转化为更大 batch、更多稳定并发、更低尾延迟或更低单位成本。

### 3.6 从单卡到多卡：增加副本还是切分模型

- 若模型单卡放得下且单请求延迟已达标，优先增加请求级 replicas，提高总吞吐和故障隔离能力；副本不能降低单个请求的模型容量需求。
- 若单卡放不下，或单请求目标确实需要聚合计算资源，再考虑 TP/PP 等模型切分；沿用训练章的切分术语，只补充推理中的目标差异。
- 推理常见的小 batch、逐 token 同步和尾延迟目标会放大通信与等待代价，因此不能直接复制训练配置；必须比较切分后节省的计算/容量与新增通信是否落在关键路径。
- Prefill–decode 解耦、跨节点 KV 传输和复杂分布式调度只作为完整版本末尾的进阶方向，不进入方案细节。

### 3.7 固定条件验证：同时报告速度、容量、质量与成本

- 固定模型与质量边界、输入/输出长度分布、请求到达率、并发、精度、硬件和服务配置，先形成关键路径假设，再只改变一个主要杠杆。
- 单请求基准同时报告 TTFT、每 token/每步延迟、端到端时延和峰值显存；服务基准增加 P95/P99、吞吐、最大稳定并发、状态池占用和单位成本。
- 平均吞吐高但尾延迟差时，检查请求分布、排队、batch 组成、长 prefill 干扰和状态池压力；优化后输出变化时，检查精度、近似算法、步数、窗口或工作负载是否已经改变。
- 结果必须同时说明目标指标、容量变化、质量或稳定性代价、复杂度和停止条件，不展示脱离 workload 与并发条件的加速倍数。
