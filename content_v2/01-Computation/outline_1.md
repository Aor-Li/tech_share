## 0. 本章定位

### 整章的问题链

开篇抛出一个具体问题：**「实时流式生成一段 768p 视频，需要多少算力？」**

每一节都是回答它必须补上的一块拼图：

1. 要算多少次浮点运算（FLOPs 估算）
2. 用什么数据格式算（精度体系）
3. 机器一秒能算多少（算力峰值）
4. 实际能拿到多少（MFU）

最后一节把四块拼起来给出答案，并留下「为什么只能拿到峰值的 40%」这个问题交给第二章。

### 为什么以 DiT 为主线

LLM 推理基础设施的两条公理——**「decode 是访存受限的」**和**「attention 的 s² 项可以忽略」**——在视频 DiT 上**都不成立**。

如果只讲 LLM 版本，读者会把错误的结论带回自己的模型。所以本章每讲完一个公式，都要追问一句：**换成 DiT 还对吗？**

## 贯穿全章的模型规格：MiniMax H3

| 组件 | 规格 |
|---|---|
| **H3-Omni-Transformer** | 33B dense、single-stream，50 层，hidden 5376，56 heads，三维 MM-RoPE (t/h/w) |
| ├─ AdaLN 分支 | 约 13B 参数；调制输出可预计算并缓存，**纯推理部署无需加载** |
| └─ 计算路径有效参数 | **约 20B**（33B − 13B） |
| **H3-VisualVAE** | 时序因果，空间 16× / 时间 4× 压缩，24 潜通道（f16t4d24） |
| └─ Patchify | 1×2×2 (t,h,w) → **等效空间 32×、时间 4×** |
| **H3-AudioVAE** | 32 kHz 每声道 → 40 Hz 潜序列，立体声 |
| **文本/视觉编码器** | Qwen3-VL-32B，取第 50 层隐状态 |
| **推理全栈参数量** | 约 69.2B（编码器 + 生成器 + VAEs） |
| **输出能力** | 24fps 原生 2K，最长 15 秒，同步立体声 |

> ⚠️ **写作前需核对**
> - vLLM 部署文档写的是 **52 个 block** 的 joint video/audio DiT（BF16 66.3 GB），与「50 层」有出入
> - FFN 扩张比、head_dim 等细节均按标准 Transformer 假设推导，须拉 `config.json` 校准
> - 否则 §1.2 的参数量验算会露怯

### 🔑 开篇钩子

33B 里有 **13B 是 AdaLN**，而 AdaLN 的调制向量**每个 timestep 只算一次、与 token 数无关**。

所以「33B 模型 → 每 token 66 GFLOPs」是**错的**，真正走 token 计算路径的只有约 20B。

> **这个反例就是第一章的开场白**：参数量和计算量在 DiT 上不是同一回事——这在 LLM 里几乎从不出错，在 DiT 上却是常态。

## 1.1 一切都是矩阵乘

### 公式

```
[m,k] × [k,n] 的 GEMM = 2mkn FLOPs        （乘、加各算一次）
```

### 要建立的概念

Transformer 里 95%+ 的浮点运算集中在少数几个 GEMM 上，所以「数 FLOPs」约等于「数矩阵乘」。

### 📊 静态图 · H3 单 block 结构与 FLOPs 分布

- 画出 H3 单个 block：self-attn + cross-modal attn + FFN + modality-specific AdaLN
- **按 FLOPs 占比着色**
- 视觉冲击点：**AdaLN 分支占 40% 的参数、却几乎看不见色块**
- 附带效果：LayerNorm / Softmax 在计算量上几乎不可见 → 为第二章（访存）埋伏笔

---

## 1.2 前向 2N —— 以及「N 到底是多少」

### 公式

```
每 token 前向 ≈ 2N FLOPs
```

推导：每个权重恰好参与一次乘加，所以 FLOPs 直接正比于参数量。

### H3 的关键修正

```
N_effective ≈ 20B  →  每 token 约 40 GFLOPs
```

**当场验算**（演示如何用架构参数反推）：

```
50 层 × 12 × 5376² ≈ 17.3B      ← 与 20B 量级吻合
```

### H3 的 token 是怎么来的

```
每潜帧 token 数 = (W / 32) × (H / 32)
潜帧率        = 24fps / 4 = 6 帧/秒
```

| 配置 | 每潜帧 token | 5 秒 | 15 秒 |
|---|---|---|---|
| 1344×768（官方 release shape） | 1,008 | **30,240** | **90,720** |
| 2560×1440（2K） | 3,600 | **108,000** | **324,000** |

### 反直觉结论：音频几乎白送

40 Hz × 立体声，15 秒才约 1,200 token，占总序列 **0.4%**。

> 「音画同生」在计算账上几乎不花钱——这个结论值得单独点出。

### 🎛️ 动态图 · Token 数计算器

- 滑块：分辨率 / 时长 / 帧率 / VAE 压缩比 / patch size
- 实时输出：token 数、单步 FLOPs
- 同一轴上标出 LLM 的 4K / 128K 上下文位置作参照
- **教学目标**：让读者亲手拖出「分辨率是平方、时长是线性、三者相乘爆炸」的感觉

## 1.3 训练的 6ND

### 公式

```
C ≈ 6ND
```

### 反向为什么是前向的两倍

反向要算两组梯度：
- **dX**：对输入的梯度，用于继续向前传播
- **dW**：对权重的梯度，用于参数更新

各需一次同规模 GEMM。

### 🎛️ 动态图 · 前向/反向 FLOPs 累加

- 一个小计算图，点击可分别展开 forward / dX / dW 三条链路
- 实时累加 FLOPs 计数器，直观呈现 2N → 6N

### DiT 特有的两个坑

1. **N 的口径**：训练时 AdaLN 分支**要算梯度**，推理时可缓存 → 训练与推理的有效参数量不同
2. **没有步数乘子**：扩散训练每样本随机采一个 timestep 前向一次，训练侧不乘 steps（与 §1.5 形成鲜明对照）

## 1.4 Attention 的 s² 项 —— 用 H3 的数把 LLM 结论打翻

> ⭐ **本章第一重点**

### 公式

```
attention / linear ≈ s / (6h)
```

H3 的 `6h = 6 × 5376 = 32,256`

### 📊 静态表 · 五个场景的比值对照

| 场景 | s | 比值 |
|---|---|---|
| LLM 对话（h=4096, s=4K） | 4,096 | **0.17** |
| H3 768p / 5s | 30,240 | **0.94** |
| H3 768p / 15s | 90,720 | **2.8** |
| H3 2K / 5s | 108,000 | **3.3** |
| H3 2K / 15s | 324,000 | **10.0** |

### 加粗结论

> **H3 在最长配置下，注意力的计算量是全部线性层的 10 倍。**
> LLM 时代「attention 可忽略、6ND 够用」的直觉在这里彻底失效。

### 架构选择是被这张表逼出来的

- **高压缩 VAE**：官方称带来 4× 有效序列长度收益 → s² 项直接除以 16
- **原生稀疏注意力**：训练末期引入以降低长序列开销（稀疏实现未包含在首个开源版本中）

### 🎛️ 动态图 · Attention 占比曲线

- 横轴：token 数（对数轴）
- 纵轴：attention FLOPs 占比
- **打点标注上表五个场景**，形成从 LLM 到视频的连续谱
- 滑块：hidden size、注意力形态（3D full / 时空分离 / 窗口稀疏 / 流式因果）
- **教学目标**：读者自己拖出「什么时候不能再忽略」的那条分界线

## 1.5 扩散推理的计算结构

> LLM 材料里完全没有对应物的一节

### 总公式

```
推理 FLOPs ≈ steps × cfg × (2·N_eff·s + 4·L·s²·h) + VAE解码 + 编码器
```

### H3 768p / 5s 单步实算

| 项 | FLOPs |
|---|---|
| 线性层 | 1.2 PFLOPs |
| 注意力 | 1.0 PFLOPs |
| **单步合计** | **≈ 2.2 PFLOPs** |

### 端到端

```
50 步 × CFG 2 × 2.2 PFLOPs = 220 PFLOPs
```

单张 H100（1 PFLOPS BF16 峰值，MFU 40% → 400 TFLOPS）：

> **约 9 分钟生成 5 秒视频 = 110 倍于实时**

### 📊 静态表 · 推理成本的三个杠杆

| 杠杆 | 收益 |
|---|---|
| 50 步 → 4 步蒸馏 | **12.5×** |
| CFG 2 → 1（distilled CFG / CFG-free） | **2×** |
| 二者叠加 | 220 → **8.8 PFLOPs**，单卡 22 秒 |

> 步数是推理成本上**最大的单一杠杆**，LLM 侧没有任何技术能给出这个量级的收益。

### 别忘了 VAE

VAE 解码工作在**未压缩的像素域**，2K 输出时绝对 FLOPs 与激活都不小。

> 证据：vLLM 的 H3 部署配方专门为它上了 VAE patch 并行与 tiling。

### 📊 静态图 · 端到端耗时堆叠条形

- 两根柱对比：`50 步 + CFG` vs `4 步 + 无 CFG`
- 每根柱分段：denoise / VAE decode / text encoder
- 把「220 PFLOPs」和「一次 LLM 对话」「训一个 7B 模型」放在同一根对数轴上比较

## 1.6 流式推理改变了什么

### 先说清楚一件事

H3 本身是**全序列双向的一次性生成，不是流式模型**。

本节讨论的是**在这类架构上做分块自回归**时账目怎么变——把 H3 当基线，流式改造是 delta。

### 公式

```
第 n 个 chunk 的注意力项 ∝ s_chunk × (s_chunk + s_history)
```

即**随生成进度线性增长**。

用 H3 的数：chunk = 1 秒 = 6,048 token，生成到第 5 秒时历史已 3 万 token，
**单块注意力开销比第 1 块高约 5 倍**。

### ⚠️ 全章最重要的一条对照

| | LLM decode | DiT 流式 |
|---|---|---|
| 每步计算的 token 数 | 1 | **6,048** |
| 算术强度 | ≈ 1 | 高 2–3 个数量级 |
| 瓶颈 | **访存受限** | **仍然计算受限** |

**推论**：continuous batching 的收益模型、投机解码、权重量化优先——这一整套 LLM 推理优化的**前提在 DiT 流式上不成立**。

> 你们的杠杆在**步数、注意力复杂度、算力效率**上，不在访存上。

### 🎛️ 动态图 · 单块耗时随进度增长

- 横轴：生成进度（第 n 个 chunk）
- 纵轴：单块耗时
- 三条曲线对比：full history / 滑动窗口 / 历史压缩
- **教学目标**：说明流式生成为什么会「越生成越慢」，以及三种缓解手段的形状差异

## 1.7 精度体系

### 📊 静态图 · 数据格式解剖

- FP32 / TF32 / FP16 / BF16 / FP8(E4M3, E5M2) / FP4 的**符号-指数-尾数位域条形对比**
- 配套：「动态范围 × 有效精度」二维定位图，把所有格式摆在同一张图上

### 核心结论

> **BF16 用精度换动态范围**，所以训练不需要 loss scaling 而 FP16 需要——这是 BF16 成为默认的根本原因。

### 混合精度

FP32 主权重副本 + BF16 计算 + FP32 累加，三者各自的作用。

### FP8

为什么必须配 scaling；per-tensor delayed scaling 与 per-block 的差别（点到为止）。

### DiT 特有：误差沿步数累积

- LLM 一次前向的数值误差不会传递进下一个 token 的计算内部
- **扩散的 N 步去噪是串联的**，低精度误差会沿步数累积
- 推论：DiT 量化的容忍度必须按**最终视觉质量**评估，不能看单步误差
- 有趣的交互：步数蒸馏到 4 步，反而降低了误差累积风险 → 量化与蒸馏是耦合的

### 分模块精度策略

| 模块 | 建议 |
|---|---|
| DiT 主干 | 可 FP8 |
| Attention | 正在往 FP8 走 |
| VAE decode | 保守，通常保留高精度 |
| AdaLN 缓存 | 可独立定精度（H3 特有） |

### 数值印象

> 精度每降一档，硬件峰值大致翻倍。

## 1.8 算力峰值：读懂 NVIDIA 的 spec sheet

### 公式

```
峰值 = SM 数 × 每 SM 每周期 Tensor Core MAC 数 × 2 × 频率
```

### 📊 静态图 · 代际峰值增长

- 柱状图，对数纵轴，按精度分组
- A100 / H100 / H200 / B200 的 BF16、FP8 **稠密**峰值
- 写作时逐个核对官方数据

### 三个坑（本节的实际价值）

1. **稀疏峰值 = 稠密 × 2**，宣传数字常用前者
2. **TF32 只是 FP32 的入口**，实际走 Tensor Core
3. **标称频率 ≠ 持续功耗下的实际频率**

### 数值锚点

> **H100 SXM ≈ 1 PFLOPS BF16（稠密）**——记住这个数就够推大部分账。

### DiT 相关的一句

H3 单个 DiT BF16 就要 66.3 GB，编码器另需 51.5 GB。

社区在 2×RTX 5090（32GB）上要靠分布式 layerwise offload、只保留 20 层常驻。

> **显存与算力的配比选择，在 DiT 上和 LLM 完全不同。**
> H20 这类「高显存低算力」的卡对 LLM decode 友好，对 DiT 反而吃亏。

## 1.9 MFU：从峰值到现实

### 公式

```
MFU = 实际 FLOPs/s ÷ 峰值 FLOPs/s
```

MFU vs HFU 的区别：重计算的 FLOPs 算不算进分子。

### 典型区间

| 场景 | MFU |
|---|---|
| LLM 稠密训练 | 35–50% |
| LLM MoE 训练 | 更低 |
| LLM decode | **< 5%** |
| **DiT 推理** | **天然较高**（始终计算受限） |

> **好消息**：不容易被带宽卡死。
> **坏消息**：没有「白捡」的优化空间，只能真刀真枪减 FLOPs。

### 🎛️ 动态图 · 双栏 MFU 瀑布

> ⭐ **本章压轴图**

- **左栏 LLM decode**、**右栏 H3 流式**，并列同一坐标
- 瀑布分段：峰值 → 非 GEMM 算子 → 访存受限 → 通讯 → 流水气泡 → 实际 MFU
- 两栏的损失项构成完全不同，**一图说清两类系统优化重心的分岔**
- 附带作用：每一段损失都对应本书后面某一章 → 这张图同时是全书路线图

### 🎛️ 动态图 · 实时性预算表

> ⭐ **本章压轴推演**

- 给定目标：24fps 实时流式输出 = 每秒 6,048 token
- 反推每秒可用 FLOPs 预算
- 再倒推可行组合：`分辨率 × 步数 × 注意力形态 × 卡数`
- 从「单卡 220 PFLOPs / 9 分钟」出发，一步步逼到实时需要什么条件

## 1.10 速查卡与过渡

### 📊 静态图 · 一页速查卡

H3 与 LLM **双栏对照**的公式与数值锚点：

| | LLM | H3 / 视频 DiT |
|---|---|---|
| 每 token 前向 | 2N | 2N_eff（注意 AdaLN） |
| 训练总量 | 6ND | 6N_eff·D，无步数乘子 |
| attn 占比 | s/(6h) ≈ 0.17 | 0.94 ~ 10 |
| 推理成本 | 2N/token | steps × cfg × (...) |
| decode/流式瓶颈 | 访存受限 | **计算受限** |

### 过渡到第二章

> **「既然一直是计算受限，第二章的访存分析还有意义吗？」**
>
> 有——VAE 解码、norm 类算子、以及流式的历史 KV，恰恰是访存侧的大头。
