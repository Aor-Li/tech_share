第一章 · 计算

算力账怎么算：FLOPs → 精度 → 峰值 → MFU

本章任务

开篇抛出一个具体问题：「实时流式生成一段 768p 视频，需要多少算力？」 回答它要补齐四块拼图：① 要算多少次浮点运算（FLOPs 估算）② 用什么数据格式算（精度体系） ③ 机器一秒能算多少（算力峰值）④ 实际能拿到多少（MFU）。

LLM 推理基础设施的两条公理——「decode 是访存受限的」「attention 的 s² 项可以忽略」——不是普适真理， 而是在特定条件下成立的经验规则。本章逐条讲清楚它们的成立边界， 并用一个视频 DiT 例子（MiniMax H3）做验证，而不是反过来讲一个模型的规格书。

本章验证用例（非主角）· MiniMax H3，视频 DiT

33B dense / 50 层 / hidden 5376 · AdaLN 分支 ≈13B 可预计算缓存 → 计算路径有效参数 N_eff ≈ 20B · VAE 空间16×/时间4×压缩 · 输出 24fps 原生2K、最长15秒、同步立体声。

1.1 一切都是矩阵乘

[m,k] × [k,n] 的 GEMM = 2mkn FLOPs（乘、加各算一次）。 Transformer 里 95%+ 的浮点运算集中在少数几个 GEMM 上，所以「数 FLOPs」约等于「数矩阵乘」—— 这对任何 Transformer 变体（LLM、DiT）都成立，是全章的通用起点。

1.2 前向 2N，以及「N 到底是多少」

每 token 前向 ≈ 2N FLOPs——每个权重恰好参与一次乘加，FLOPs 直接正比于参数量。 这条公式对任何 dense Transformer 都成立，关键是先弄清楚 N 该怎么数。

验证：H3 的 N 不是 33B

AdaLN 不参与逐 token 计算 → N_eff≈20B，每 token 约 40 GFLOPs。 架构参数反推：50层×12×5376² ≈ 17.3B，与 20B 量级吻合。

token 数是平方项×线性项

对图像/视频类模型：分辨率是平方项，时长是线性项，二者相乘容易爆炸——这是设计任何多维序列系统时的通用直觉。

附带一句通用观察：多模态系统里非视觉轨（如音频）在 token 预算里的占比通常远小于视觉轨—— H3 的音频轨 15 秒仅约 1,200 token，占比 0.4%，只是一个例证，不是本节重点。

1.3 训练的 6ND

C ≈ 6ND。反向要算两组梯度：dX（对输入的梯度，用于继续向前传播）、 dW（对权重的梯度，用于参数更新），各需一次同规模 GEMM——2N（前向）+2N（dX）+2N（dW）=6N， 对任何 Transformer 训练都成立。

验证：扩散这一类架构的两个共性例外——训练时调制分支（如 AdaLN）要算梯度而推理时可缓存，训练与推理的有效参数量不同； 扩散训练每样本只随机采一个 timestep 前向一次，训练侧不乘步数（与 1.5 节推理侧的「steps × cfg」形成对照）。

1.4 Attention 的 s² 项：什么时候不能再忽略

attention / linear ≈ s / (6h)——全章最重要的一个判据，适用于任何 Transformer： 序列长度 s 相对 hidden h 越大，attention 占比越高。LLM 场景 s 通常远小于 6h，所以「attention 可忽略」 是一条在特定 s/h 区间下成立的经验规则，不是公理。

场景s比值
LLM 对话（h=4096, s=4K）4,0960.17
长序列例 / H3 768p·5s（h=5376）30,2400.94
长序列例 / H3 768p·15s90,7202.8
长序列例 / H3 2K·5s108,0003.3
长序列例 / H3 2K·15s324,00010.0
不是「DiT 需要不同的公式」，而是「同一个公式，token 数一旦跨过 6h 这个尺度，结论就会反转」。

这是可迁移到任何长序列系统（长文档、长视频、长音频）的判断方法，视频 DiT 只是恰好最容易越过这条线的一类例子。

1.5 扩散模型推理的计算结构（补充公式）

这是 LLM 材料里没有的一类计算结构——不是「DiT 特有」，而是扩散/迭代式生成模型这一类方法共有的结构： 推理 FLOPs ≈ steps × cfg × (2·N_eff·s + 4·L·s²·h) + 解码 + 编码。

1.6 流式推理与 LLM decode 的本质差异

LLM decode分块自回归的迭代式生成
每步计算的 token 数1远大于 1（验证例：H3 chunk=6,048）
算术强度≈ 1高 2–3 个数量级
瓶颈访存受限仍然计算受限
任何「每步处理 token 数远大于 1」的自回归系统，都不能直接套用 LLM decode 的优化经验。

continuous batching、投机解码、权重量化优先——这套前提在这类系统上不成立；杠杆在步数、注意力复杂度、算力效率上。

补充说明：H3 本身是全序列双向的一次性生成，不是流式模型；这里讨论的是"假设做分块自回归会怎样"的推演，用它的 chunk 数字（5秒时历史约3万 token，单块开销涨约5倍）给出具体量级。

1.7 精度体系

BF16 用精度换动态范围，所以训练不需要 loss scaling 而 FP16 需要——这是 BF16 成为默认的根本原因。
混合精度三件套

FP32 主权重副本 + BF16 计算 + FP32 累加。

FP8 必须配 scaling

per-tensor delayed scaling 与 per-block 的差别，点到为止。

误差沿步数累积（迭代式生成通用）

N 步迭代是串联的，低精度误差会沿步数累积——不只 H3 如此，容忍度要按最终输出质量评估。

数值印象：精度每降一档，硬件峰值大致翻倍。分模块精度策略举例（验证例，来自 H3）：主干可 FP8，attention 正在往 FP8 走， 解码器保守保留高精度，调制分支（AdaLN）缓存可独立定精度——最后一条是 H3 具体实现，供参考。

1.8 算力峰值：读懂 spec sheet

峰值 = SM 数 × 每 SM 每周期 Tensor Core MAC 数 × 2 × 频率——完全通用，与具体模型架构无关。

三个坑

稀疏峰值=稠密×2，宣传常用前者；TF32 只是 FP32 的入口，实际走 Tensor Core；标称频率≠持续功耗下的实际频率。

≈ 1 PFLOPS H100 SXM BF16（稠密）——记住这个数就够推大部分账。

显存与算力的配比选择，在计算密集型架构（如 DiT）和访存密集型场景（如 LLM decode）上导向不同的硬件选型—— 验证例：H3 单个 DiT BF16 就要 66.3GB，"高显存低算力"的卡对 LLM decode 友好，对 DiT 反而吃亏。

1.9 MFU：从峰值到现实

MFU = 实际 FLOPs/s ÷ 峰值 FLOPs/s；MFU vs HFU 的区别在于重计算的 FLOPs 算不算进分子。

场景MFU

LLM MoE 训练更低
LLM decode< 5%
计算受限的迭代式生成系统天然较高
