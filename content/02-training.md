## 2.1 先拆开一个训练 step

训练的工作单元不是一次 forward，而是一次参数更新。最简化的时间线包含三段：

```text
forward                 backward                 optimizer step
读参数与输入             读激活与参数              读梯度与优化器状态
产生并保留部分激活        产生梯度、逐步释放激活       更新参数与优化器状态
```

当一张卡容不下目标 batch 时，一次更新还会被拆成多个 micro-step。假设每卡 micro-batch 为 `m`，梯度累积次数为 `a`，数据并行副本数为 `d`，则忽略最后一个不完整 batch 时：

```text
global batch = m × a × d

micro-step 1: forward → backward → 梯度累积 ┐
micro-step 2: forward → backward → 梯度累积 │
micro-step 3: forward → backward → 梯度累积 ├─ optimizer update
micro-step 4: forward → backward → 梯度累积 ┘
```

这里有三个容易混淆的口径：micro-batch 决定一次 forward/backward 的局部形状；gradient accumulation 表示一次更新前执行多少个 micro-step；global batch 才是一次参数更新共同贡献的样本总数。改变其中一个量时，要明确另外两个量和卡数是否固定。

一次训练更新可以先写成两本简化账。

| 账本 | 主要项目 | 第一判断 |
| --- | --- | --- |
| 显存账 | 参数、梯度、优化器状态、当前及保留激活、临时空间、通信 buffer | 峰值时哪些项目同时存活 |
| 时间账 | 多次 forward、多次 backward、一次参数更新、通信与等待 | 哪一项在关键路径上，能否与其他工作重叠 |

参数、梯度和优化器状态主要随模型规模变化；激活主要随 micro-batch、序列长度、隐藏维度、层数以及保存策略变化；临时空间取决于算子实现。不能把“每参数若干字节”当作训练峰值显存，因为它遗漏了形状敏感的激活和运行时空间。

“跑不快”也必须带口径。`step time` 衡量一次 optimizer update 的墙钟时间；samples/s 或 tokens/s 衡量单位时间完成的有效数据量。若 global batch 改了，单比 step time 会误导。MFU 通常把实测有效模型计算量与硬件理论峰值比较；HFU 还可能把重计算等实际硬件工作计入分子。二者定义不统一时，只比较同一实现、同一口径的结果，不把指标名当成结论。

这份账本最终把问题分成三类：单卡容量不够；单卡计算粒度太小或供给不足；多卡通信与等待抵消了新增算力。后续配置分别针对这些问题。

## 2.2 单卡先做三类资源交换

> **HTML 展示标注**：本节需要展示或说明 Activation Checkpointing 的执行方法，至少呈现 forward 只保存检查点、backward 从检查点重算其余激活的过程，以及“用额外计算换显存”的结果。

先假设目标 global batch 不变，单卡执行四个 micro-step。三类常见配置改变的是同一份账本，而不是三个互不相关的技巧。

| 方法 | 直接改变 | 换来什么 | 付出与边界 |
| --- | --- | --- | --- |
| 混合精度 | 参数、激活或梯度的每元素字节数，以及可用计算路径 | 更低容量和搬运压力；合适硬件上计算更快 | 某些归约或更新仍需较高精度；溢出、下溢和收敛必须验证 |
| 减小 micro-batch、增加累积 | 每个 micro-step 的激活峰值下降，micro-step 数增加 | 在相同 global batch 下缓解单次峰值 | 总样本工作量没有消失；小 shape 可能降低算子效率，固定开销被重复支付 |
| Activation Checkpointing | forward 只保存选定边界的激活 | backward 前的激活驻留显著减少 | backward 时重做部分 forward，增加 FLOPs 与 step time |

可以把它们放在一条因果链上看：若峰值来自激活，先减小 micro-batch 会缩小激活；累积把 global batch 补回来；仍然放不下时再减少保存的激活。若峰值主要来自参数、梯度或优化器状态，继续减 micro-batch 的收益会迅速变小，此时应转向状态分片。

混合精度也不等于“所有张量统一改成低精度”。训练中可能同时存在低精度计算副本、较高精度更新状态以及不同精度的归约。具体组合由算法和框架决定，正确的验证对象是峰值显存、step time 与训练质量，而不是配置名。

最后检查输入形状。大量 padding 会让 GPU 对无效 token 做真实计算；packing 可以提高有效 token 比例，却也会改变样本边界和实现复杂度。数据加载不及时则会让 GPU 等待。它们都表现为利用率低，但既不是显存分片问题，也不应直接用“加卡”解决。

## 2.3 多卡并行先问“切什么”

单卡交换仍不够时，把训练对象沿不同维度分布到多卡：

```text
一个训练工作负载
├─ batch            → Data Parallelism
├─ 训练状态          → ZeRO / FSDP
├─ 层内张量          → Tensor Parallelism
├─ 连续层            → Pipeline Parallelism
├─ 序列 / 上下文      → SP / CP
└─ 专家              → Expert Parallelism
```

所有方法都用四问理解：每卡少持有什么；每卡少算什么；为恢复下一步所需布局要交换什么；新增通信、等待或算法约束是什么。不同维度可以组合，但组合不会取消各自代价，只会让布局转换和设备映射更重要。

一个实用的选择顺序是：完整训练副本放得下且单卡计算粒度足够时，先用 DP 扩大数据吞吐；训练状态放不下时分片状态；单层本身太大时切层内张量；总层数跨卡驻留时切层；长序列激活或 Attention 成为瓶颈时切序列；MoE 专家参数和计算需要分布时切专家。

## 2.4 切 batch 与训练状态：DP、ZeRO 和 FSDP

### DP：复制模型，切 batch

数据并行让每卡保留完整训练副本，各自处理不同 micro-batch。backward 后，各卡梯度必须归约成一致结果，再进行相同更新。

```text
GPU 0: 完整状态 + batch 分片 0 ─┐
GPU 1: 完整状态 + batch 分片 1 ─┼─ AllReduce(梯度) → 各卡一致更新
GPU 2: 完整状态 + batch 分片 2 ─┤
GPU 3: 完整状态 + batch 分片 3 ─┘
```

DP 增加的是聚合数据吞吐，不降低完整模型及训练状态的单卡容量要求。固定 global batch 时，增加 DP degree 会减少每卡数据；如果局部 micro-batch 小到计算效率下降，或者梯度同步不能被 backward 重叠，扩展效率就会变差。

### ZeRO：逐级减少状态复制

ZeRO 从传统 DP 的完整副本出发，逐级分片训练状态：

| 阶段 | 分片对象 | 每卡不再完整复制什么 | 运行时新增需求 |
| --- | --- | --- | --- |
| ZeRO-1 | 优化器状态 | 优化器状态 | 更新后让各卡获得一致参数 |
| ZeRO-2 | 优化器状态、梯度 | 再减少完整梯度副本 | 将归约结果直接分散到负责设备 |
| ZeRO-3 | 优化器状态、梯度、参数 | 再减少完整参数副本 | 计算前按需聚合参数，之后再次分片或释放 |

stage 越高，单卡长期驻留状态越少，但参数或结果的聚合更频繁，通信和临时峰值也更敏感。“总分片量能放下”仍不代表运行时峰值一定能放下。

### FSDP：按层看参数的完整生命周期

理解 FSDP 的关键不是把它贴成某个 ZeRO stage，而是跟踪一个参数单元：平时只持有分片；计算前 AllGather 成完整参数；局部 forward/backward 使用它；不再需要时释放完整副本；梯度通过 ReduceScatter 归并并重新成为分片。

```text
参数分片驻留 → AllGather → 完整参数参与计算 → 释放完整参数
梯度分片驻留 ← ReduceScatter ← 各卡产生局部梯度
```

分片粒度、预取和释放时机决定通信能否与计算重叠，也决定同时聚合多少参数。FSDP 与 ZeRO-3 共享“参数、梯度和优化器状态分片”的核心思想，但封装单位、生命周期调度和实现行为不能仅凭名称视为完全相同。

## 2.5 切层内张量：Tensor Parallelism

当一个层本身放不下，或希望多卡共同计算一个层时，可以切矩阵。以两层 MLP 为例：

```text
H ── W_up ──→ 4H ── 激活 ── W_down ──→ H
```

先把 `W_up` 的输出列切到两卡，每卡只产生一半中间特征：

```text
GPU 0: X · W_up[左半]  → Z0
GPU 1: X · W_up[右半]  → Z1
```

再让 `W_down` 按与中间特征对应的输入行切分，各卡计算局部贡献：

```text
GPU 0: Z0 · W_down[上半] → Y0 ┐
GPU 1: Z1 · W_down[下半] → Y1 ├─ AllReduce / ReduceScatter → Y
```

这样中间无需先拼成完整 `Z`，但下一个需要完整或另一种布局的算子之前，必须归并局部贡献。TP 直接降低单层权重与部分中间张量的单卡占用，并并行单层计算；代价是层内频繁 collective，对消息大小、互联和布局连续性敏感。

所以 TP 的判断条件是“单层容量或单层计算需要跨卡”，不是“手里有多张卡”。层很小、局部矩阵变窄时，通信与小粒度计算可能比节省的时间更贵。

## 2.6 切层：Pipeline Parallelism

PP 把连续层分给不同 stage。相邻 stage 通过点对点通信传递激活，backward 再反向传递激活梯度。它降低每卡驻留层数，但同一个 micro-batch 仍必须依次经过所有 stage。

若只有一个 micro-batch，大部分 stage 都在等待。把 batch 拆成多个 micro-batch 后才能流水执行。用 `F1/B1` 表示 micro-batch 1 的 forward/backward：

```text
GPipe:  F1 F2 F3 F4 | B4 B3 B2 B1
1F1B :  预热若干 F  | F 与 B 交替 | 排空
```

GPipe 的规则直观，但在 backward 开始前会保留更多在途 micro-batch 激活。1F1B 在稳定阶段交替 forward 与 backward，通常降低同时存活的激活数量；两者都无法消除流水线的预热与排空。

PP 的主要代价有三项：最慢 stage 决定整条流水线节拍；首尾阶段存在空泡；跨 stage 的依赖和激活传输进入关键路径。增加 micro-batch 数可以摊薄空泡，却可能改变累积、显存与调度。interleaved 调度让设备承担多个虚拟 stage，zero-bubble 一类工作继续重排任务以减少空泡；主线只需知道它们优化的是调度等待，不会消除 stage 平衡与依赖约束。

## 2.7 切序列或上下文：SP、CP、Ring Attention 与 Ulysses

长文本和长视频会让激活及 Attention 状态随序列增长。序列方向的切分用于分摊这些张量，但术语要结合框架阅读：SP 常与 TP 配合，把原本在 TP 组内复制的非 TP 区域激活沿序列切开；CP 更进一步，让长上下文的 Attention 计算和相关状态跨设备分布。二者不应仅凭名字视为同一种实现。

Ring Attention 让每卡固定保留自己的 query 分块，KV 分块沿设备环移动：

```text
第 0 轮：Q0×KV0   Q1×KV1   Q2×KV2   Q3×KV3
第 1 轮：Q0×KV3   Q1×KV0   Q2×KV1   Q3×KV2
    …直到每段 Q 看过所需的 KV 分块
```

每卡边接收下一块 KV，边更新本地 Attention 结果。它避免每卡长期保存完整上下文，但环上传输、同步以及计算通信重叠成为新约束。

Ulysses 采用另一种布局转换。开始时各卡持有不同序列分片；通过 All-to-All，把布局改成各卡持有完整序列范围中的一部分 attention heads；完成局部 Attention 后，再通过 All-to-All 恢复序列切分布局。

```text
[局部序列 × 全部 heads]
        └─ All-to-All → [完整序列 × 局部 heads]
                         └─ Attention
        ← All-to-All ─── [完整序列 × 局部 heads]
```

两者解决的核心问题相同：让单卡不再承担完整长序列的激活或 Attention 工作；数据移动方式不同。选择时要看序列长度、head 数的可切分性、互联和实现支持，而不是只比较名称。

## 2.8 切专家：Expert Parallelism

MoE 层只把每个 token 路由到少量专家，但全部专家参数仍可能很大。EP 把不同专家放到不同设备，执行路径是：

```text
各卡输入 token
   → router 选专家
   → All-to-All dispatch：token 去专家所在设备
   → 本地专家计算
   → All-to-All combine：结果回到原布局
```

例如四个专家分布在四卡，如果路由结果为 `E0: 6, E1: 4, E2: 4, E3: 2`，最快设备也必须等待处理 6 个 token 的设备，除非实现通过容量限制、丢弃、重路由或其他机制处理不均衡。EP 分摊专家参数与专家计算，但 All-to-All、token 数波动、专家负载不均和路由等待可能成为瓶颈。

因此，MoE 的“每 token 只激活少量参数”不等于通信很少，也不保证每卡工作量均匀。主讲只需追踪 token 在 dispatch 和 combine 前后的归属，并观察每专家 token 数与等待时间。

## 2.9 用资源交换表完成选择

| 切分对象 | 代表方法 | 主要降低的单卡压力 | 新增通信 | 主要代价或等待 | 优先解决 |
| --- | --- | --- | --- | --- | --- |
| batch | DP | 单卡数据工作量 | 梯度 AllReduce | 小局部 batch、同步暴露 | 副本放得下时扩大数据吞吐 |
| 训练状态 | ZeRO / FSDP | 参数、梯度、优化器状态 | AllGather、ReduceScatter 等 | 聚合临时峰值、频繁通信 | 状态主导的 OOM |
| 层内张量 | TP | 单层参数、中间张量与计算 | 层内聚合或归并 | 高频 collective、小粒度计算 | 单层放不下或单层计算过重 |
| 层 | PP | 每卡驻留层数 | stage 间 send/recv | 空泡、stage 不平衡 | 总层数跨卡驻留 |
| 序列 / 上下文 | SP / CP | 长序列激活、Attention 状态与计算 | 归并、环传输或 All-to-All | 同步、布局约束 | 长文本或长视频序列瓶颈 |
| 专家 | EP | 专家参数与专家计算 | token All-to-All | 负载不均、容量与路由等待 | MoE 专家无法单卡承载 |

面对 OOM，先看峰值时间线：激活主导时优先比较 micro-batch、累积、重计算与序列切分；训练状态主导时比较状态分片；单层临时峰值主导时再考虑 TP。面对低单卡利用率，先检查局部 shape、padding、数据供给和固定开销。面对多卡扩展差，再检查 collective 是否暴露、PP 空泡、专家不均和不可重叠等待。

最后用同一套实验纪律收口：固定模型、数据、global batch、精度和质量边界；记录峰值显存、step time 与有效 samples/s 或 tokens/s；一次只改变一个杠杆。一个可验证的判断应该写成：

> 峰值出现在 forward 末尾，随 micro-batch 近似增长，而参数与优化器状态不变；先将 micro-batch 减半并把累积翻倍，验证 global batch 不变时峰值是否下降、吞吐损失是否可接受。

而不是：

> OOM 了，所以直接上更多卡和更多并行。
