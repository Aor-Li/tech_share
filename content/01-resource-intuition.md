## 1.1 一组张量运算需要多少资源和时间？

看到一组张量运算时，很自然会问：它要用多少资源，又要运行多久？这个问题不能只看参数量或设备型号。面对一个算子、一个 block，甚至一整个模型，可以先画三本账：

| 账本 | 先问什么 | 基础单位 | 它能回答什么 |
| --- | --- | --- | --- |
| 计算账 | 做了多少乘法、加法和其他运算？ | FLOPs | 需要多少计算工作量，理论上最快能算多久 |
| 驻留与搬运账 | 哪些张量要同时放在显存里？执行时实际读写多少？ | bytes | 放不放得下，更可能受容量还是带宽限制 |
| 通信账 | 哪个张量要在多少设备之间、以什么频率交换？ | bytes / call | 多设备增加了什么资源，又付出了什么协同代价 |

三本账都从四个输入开始：**操作类型、张量形状、数据精度和硬件**。缺少其中任何一个，“这个算子很大”都只是模糊印象。

这里还要先约定两层答案：

- **估算**给出量级和下界，用来比较两个方案、发现数量级错误、形成瓶颈假设；
- **实测**包含具体 kernel、调度、并发和系统环境，用来确认关键路径。

后文所有公式都属于第一层。它们是地图，不是测速仪：用于先排除不合理判断，再带着更具体的瓶颈假设去测量。

## 1.2 计算工作量：从一个 GEMM 到一组 block

### 如何评估计算量

**FLOP** 是 **Floating-Point Operation** 的缩写，指一次浮点运算。估算大模型计算工作量时，通常统计完成一次任务涉及多少次这样的运算，并写成 FLOPs。

大模型里的常见操作包括：

- GEMM：线性层和 Attention 中的大规模矩阵乘法；
- Elementwise：激活函数、bias 加法、残差连接等逐元素计算；
- Reduction：沿某个维度求和、取最大值等聚合计算；归一化和 softmax 通常同时包含 Reduction 与 Elementwise。

其中，矩阵乘法通常贡献大部分 FLOPs，也最适合先用 shape 做量级估算。因此后文先估算占比最大的 GEMM，再按 Attention 和 FFN 模块汇总计算量。逐元素运算和归约并非不存在，只是在大尺寸 dense block 的第一轮估算中常被作为低阶项暂时忽略；遇到小矩阵、长序列或特殊算子时，需要重新判断。

本报告把一次乘加记作 **2 FLOPs**，因为表达式 `a × b + c` 在数学上包含一次乘法和一次加法。硬件可能用一条 fused multiply-add（FMA，融合乘加）指令完成它，但“指令条数”和“浮点运算次数”是两种口径：一条 FMA 指令仍完成了两次浮点运算。也有资料把一次乘加计为一次操作，因此比较数字前要先确认计数约定，否则结果可能相差一倍。

还要注意，FLOPs 描述的是**工作量**，不是耗时。相同的 FLOPs 可能因为数据精度、shape、数据搬运和 kernel 效率不同而花费完全不同的时间；这正是后文还要继续计算数据移动与理论时间边界的原因。

### GEMM：先读 shape，再套公式

设输入矩阵 `X` 的形状为 `[m, k]`，权重矩阵 `W` 的形状为 `[k, n]`，输出 `Y = XW` 的形状为 `[m, n]`。输出中有 `m × n` 个元素，每个元素需要沿 `k` 维完成一次点积，因此：

```text
[m, k] × [k, n] → [m, n]
总工作量 = 2 × m × k × n FLOPs
```

例如 `[2048, 4096] × [4096, 16384]`：

```text
2 × 2048 × 4096 × 16384
= 274,877,906,944 FLOPs
≈ 0.275 TFLOPs
```

这个数字只描述“要做多少工作”，还没有回答“要做多久”。

### Attention：投影线性增长，位置交互二次增长

对一组标准的全局 self-attention，记：

- `B`：独立样本数；
- `T`：每个样本的位置数；
- `D`：隐藏维度；
- `H`：头数；
- `d`：每头维度，且 `D = H × d`。

Q、K、V 和输出投影都可归入 GEMM。若四个投影权重均为 `[D, D]`，它们的前向计算量合计为：

```text
4 个投影：2 × B × T × 4D² FLOPs
```

位置之间的交互包含两次主要矩阵乘法：

```text
QKᵀ：2 × B × T² × D FLOPs
AV ：2 × B × T² × D FLOPs
合计：4 × B × T² × D FLOPs
```

因此，投影项随 `T` 线性增长，位置交互项随 `T²` 增长。这是形状关系，不代表实际时间一定被 Attention 主导：投影和 FFN 的常数项可能更大，kernel 也可能避免物化完整的 score 矩阵。mask、局部窗口或稀疏模式还会改变有效计算范围，必须按实际操作重算。

### 参数量近似：好用，但要把条件写在旁边

对于一次前向中每个位置恰好使用一次的 dense 权重：

```text
每个位置、每个激活参数约做一次乘加
一次前向计算量 ≈ 2 × 位置数 × 激活参数量
```

这个近似不自动包含 Attention 的位置交互，也不适用于未激活的参数或重复调用的权重。它更适合做量级校验，而不是替代逐项计算。

### 一个无品牌的标准 block 账本

取一个简化 block：四个 `[D, D]` Attention 投影，加上 `D → 4D → D` 的两层 FFN。忽略 norm、激活函数和残差加法等低阶项，则每层用于 GEMM 的参数量约为：

```text
Attention 投影：4D²
FFN：D×4D + 4D×D = 8D²
合计：12D²
```

令 `B=1`、`T=2048`、`D=4096`、层数 `L=32`：

| 项目 | 单层 | 32 层 |
| --- | ---: | ---: |
| GEMM 参数量 | 2.013 亿 | 64.42 亿 |
| 投影与 FFN | 0.825 TFLOPs | 26.39 TFLOPs |
| 两次 Attention 矩阵乘法 | 0.0687 TFLOPs | 2.20 TFLOPs |
| 合计 | 0.893 TFLOPs | **28.59 TFLOPs** |

参数量近似给出 `2 × 2048 × 64.42 亿 ≈ 26.39 TFLOPs`，正好对应投影与 FFN；再把位置交互补上，得到约 28.59 TFLOPs。这个例子不是某个模型的规格，只用于演示“算子 → 单层 → 层堆叠”的方法。

## 1.3 数据移动：计算多，不等于一定受算力限制

同一张量至少有三个不同的“大小”概念：

1. **逻辑大小**：由 shape 和数据格式决定，例如 `num_elements × bytes_per_element`；
2. **同时驻留容量**：某一时刻必须一起存在于显存中的张量总量；
3. **累计搬运量**：执行期间跨存储层级实际发生的读写总量。

一份 100 MB 的权重在容量账上可以只有一份，但如果它被反复从 HBM 读取十次，搬运账就可能接近 1 GB。反过来，如果一个 tile 被读入片上存储后复用很多次，它只产生一次主要的 HBM 读取，却完成大量计算。

可以先把 GPU 简化成两层：

```text
HBM：容量大、离计算单元更远
  ↕  搬运数据
片上存储：容量小、访问快，适合暂存和复用 tile
  ↕
计算单元
```

这里不需要记住具体缓存层级，只需保留一个判断：**性能不仅取决于有多少数据，还取决于数据搬多远、搬几次、每次搬来后做多少计算。**

### 算术强度把两本账接起来

定义：

```text
算术强度 I = 总 FLOPs / HBM 搬运字节数
单位：FLOPs/byte
```

简化 Roofline 可以写成：

```text
可达到的性能 ≤ min(峰值 FLOP/s, 算术强度 × 峰值带宽)
```

两条上限的交点是：

```text
拐点算术强度 = 峰值 FLOP/s / 峰值带宽
```

以 H100 SXM 的 BF16 **稠密** Tensor Core 峰值约 989 TFLOP/s、HBM 带宽 3.35 TB/s 为例，理想拐点约为：

```text
989 / 3.35 ≈ 295 FLOPs/byte
```

高于这个量级，理想模型更偏向 compute-bound；低于这个量级，更偏向 bandwidth-bound。这里的“偏向”仍然是假设，不是测量结论。

回到前面的 GEMM。若假设输入、权重各从 HBM 读取一次，输出写回一次，且采用 BF16：

| shape | FLOPs | 最小逻辑搬运量 | 算术强度 | 理想判断 |
| --- | ---: | ---: | ---: | --- |
| `[2048,4096] × [4096,16384]` | 274.88 GFLOPs | 218.10 MB | 1260 FLOPs/byte | 更偏计算 |
| `[1,4096] × [4096,16384]` | 0.134 GFLOPs | 134.26 MB | 约 1 FLOP/byte | 更偏带宽 |

权重相同，只把 `m` 从 2048 改为 1，计算量和数据复用就完全不同。由此可以得到一个比“矩阵乘很耗算力”更有用的判断：**shape 决定复用，复用决定计算账和搬运账谁更可能成为上限。**

Attention 也要区分数学目标和实现。位置交互的 FLOPs 可以随 `T²` 增长，但实现并不一定把完整的 `T × T` score 矩阵写入 HBM。tiling 或 IO-aware attention 的核心直觉，就是在近似不改变数学目标的前提下，让中间结果更多地在片上复用，减少 HBM 往返。具体 kernel 是否受益，仍取决于 shape、精度和实现。

## 1.4 从工作量和数据量到理论时间边界

有了计算量和搬运量，可以分别计算两个理想下界：

```text
计算时间下界 = 总 FLOPs / 对应精度的峰值 FLOP/s
数据移动时间下界 = HBM 搬运字节数 / 峰值带宽
单设备理想时间边界 ≥ max(计算下界, 数据移动下界)
```

继续使用 H100 SXM 的 BF16 稠密口径：

| GEMM shape | 计算下界 | 带宽下界 | 理想主导侧 |
| --- | ---: | ---: | --- |
| `[2048,4096] × [4096,16384]` | 0.278 ms | 0.065 ms | 计算 |
| `[1,4096] × [4096,16384]` | 0.000136 ms | 0.0401 ms | 带宽 |

这组数的用途是建立数量级，不是承诺耗时。实际时间通常更长，常见原因包括：

- shape 太小或维度不友好，无法充分使用计算单元；
- 实际 HBM 读写多于“一次读、一次写”的最小逻辑量；
- 算子之间存在依赖、同步和空隙；
- kernel 启动、框架调度和数据准备有固定开销；
- 多设备时通信暴露在关键路径上。

如果有相似工作负载的实测利用系数，可以做经验修正：

```text
粗略时间 ≈ 理论下界 / 相似工作负载的实测利用系数
```

但“相似”至少要包含硬件、精度、shape、kernel 路径和并行布局。这里不存在一个可跨工作负载套用的通用利用率常数。经验系数只能修正估算，不能解释瓶颈来源。

## 1.5 显存容量：大小之外，还要看生命周期

显存账的第一行仍然很简单：

```text
张量容量 = num_elements × bytes_per_element
```

例如 `[8192,8192]` 的 BF16 张量包含 67,108,864 个元素，占 134.22 MB（十进制）。但要估算峰值显存，不能把运行中出现过的所有张量机械相加，而要问它们是否同时存活。

可以把通用张量分成三类：

| 类型 | 生命周期直觉 | 例子 |
| --- | --- | --- |
| 长期驻留 | 跨越大部分执行过程 | 权重、常量表 |
| 阶段性状态 | 跨越一段逻辑阶段，之后可释放或复用 | 输入、需要保留的中间状态 |
| 临时空间 | 为某个算子或通信短暂存在 | workspace、临时输出、通信 buffer |

以 `Y = XW` 为例，若 `W` 为 `[4096,16384]`、`X` 为 `[2048,4096]`、均使用 BF16：

```text
时间 ─────────────────────────────────────────→
W  134.22 MB  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
X   16.78 MB  ━━━━━━━━━━━━━━━
Y   67.11 MB            ━━━━━━━━━━━━━━━━━━━━━━━
workspace                ━━━━━
```

真正的局部峰值发生在 `W`、尚未释放的 `X`、正在生成的 `Y` 和 workspace 重叠时。执行结束后，`X` 与 workspace 可能释放，`Y` 继续存活。因此：

```text
峰值显存 = max_t(时刻 t 所有存活张量与额外空间之和)
```

还要为框架预留、内存碎片、通信 buffer 和算子 workspace 留出余量。监控里看到的 reserved memory 也不一定等于活跃张量之和。

这就是“容量”和“搬运”的边界：一份权重占多少显存是容量问题；执行期间从 HBM 读了几遍是数据移动问题。两者都用 bytes，却不能混成同一本账。

## 1.6 多设备：增加资源，也引入通信代价

增加设备，确实增加了聚合算力和物理显存，但它们并不会自动变成一个工作负载可直接使用的资源池。首先要决定张量如何布局：

- **复制**：每台设备保留完整副本，适合让不同工作彼此独立地并行；聚合吞吐可能增加，但单个工作仍受单设备容量约束；
- **切分**：每台设备只保留张量的一部分，单个工作可以使用聚合容量和计算资源；代价是某些步骤需要交换分片。

例如一个 `[8192,8192]` 的 BF16 张量逻辑大小为 134.22 MB。切到 8 台设备后，每台只驻留约 16.78 MB；但如果下一步需要完整张量，就必须重新聚合。这说明“省了 8 倍本地容量”不等于“没有额外时间”。

### 先建立拓扑层次

通信路径至少分三层：

1. **卡内**：计算单元与 HBM 之间的数据移动；
2. **本机卡间**：同一节点内的 GPU 互联；
3. **跨节点**：经过网卡和交换网络连接其他节点。

通常路径越远，可用带宽越低、延迟和共享竞争越明显。但具体快慢必须看实际机器拓扑，不能仅凭“有多张卡”推断。

### 用张量前后变化理解 collective

设有 `p` 台设备：

| 原语 | 操作前 | 操作后 | 直觉 |
| --- | --- | --- | --- |
| AllReduce | 每台都有同 shape 的 `Xᵢ` | 每台都有 `reduce(X₀…Xₚ₋₁)` | 汇总并把结果发给所有设备 |
| AllGather | 每台只有不同分片 `Xᵢ` | 每台都有拼接后的完整 `X` | 把分片聚合为完整张量 |
| ReduceScatter | 每台都有待归约的 `Xᵢ` | 每台得到归约结果的不同分片 | 一边汇总，一边拆分结果 |
| send/recv | 一台持有张量 | 指定相邻设备收到张量 | 点对点传递 |

NCCL 的语义中，ReduceScatter 后接 AllGather 与 AllReduce 等价；但实际执行时间仍取决于算法、拓扑和消息大小。这里不需要推导 ring 或 tree，只需要先画清楚张量布局如何变化。

第一步量级估算仍然是：

```text
逻辑 payload = 张量元素数 × 每元素字节数
```

它只给出要交换对象的基础大小，不等于每条物理链路上的总字节数。要判断通信是否进入关键路径，还要补四个问题：

- 消息有多大，是否小到被固定延迟主导；
- 每个工作单元调用多少次；
- 经过卡内、本机还是跨节点路径；
- 能否与独立计算重叠，还是下一步必须等待结果。

因此，多设备加速的正确表达不是“卡数翻倍，时间减半”，而是：**本地计算和容量压力降低了多少，新增通信又有多少暴露在关键路径上。**

## 1.7 一张四问资源判断卡

面对任意工作负载，按下面四问走一遍：

### 1. 算多少、搬多少？

- 从主要 GEMM、Attention 或其他核心操作的 shape 估算 FLOPs；
- 用数据格式换算逻辑 bytes；
- 区分张量容量、最小逻辑读写和实际累计搬运量。

### 2. 理论最快多少？

- 对齐硬件型号、数据精度和 dense/sparse 峰值口径；
- 分别计算计算下界与带宽下界；
- 用算术强度形成 compute-bound 或 bandwidth-bound 假设。

### 3. 放得下吗？

- 画出长期、阶段性和临时张量的生命周期；
- 取同时存活量的峰值；
- 加上 workspace、通信 buffer、框架预留和碎片余量。

### 4. 单设备不够怎么办？

- 新设备增加的是聚合计算、聚合容量，还是独立副本；
- 哪些张量复制，哪些张量切分；
- 交换什么、每次多大、多久一次、走哪条路径；
- 通信能否重叠，还是会阻塞下一步。

最终产物应该是一个可验证的判断，例如：

> “按当前 shape，最小逻辑算术强度明显低于硬件拐点；我推测 HBM 带宽比峰值算力更可能限制时间。下一步固定输入 shape 和精度，测量有效带宽与实际耗时。”

而不是：

> “GPU 没跑满，所以应该加卡。”

## 适用边界与讲述压缩

本章方法适合做一阶量级估算。它主动忽略了部分低阶算子、kernel 选择、调度细节、通信算法和框架行为，因此不能替代 benchmark 或 profiler。Attention 的数学复杂度也不能直接等同于 HBM 物化量，设备规格表中的峰值更不能当作可持续实测吞吐。

在 30 分钟压缩版中，本章保留以下链路即可：

```text
GEMM shape → FLOPs
FLOPs + bytes → Roofline 与时间下界
张量生命周期 → 峰值容量
```
