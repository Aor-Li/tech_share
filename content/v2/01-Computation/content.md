## 主线是 infra 概念，不是 MiniMax H3

这是本稿相对 outline 草稿的一处重要收敛：**MiniMax H3 只是贯穿全章的一个具体例子**，用来把公式落到可核验的数字上；
每一小节都要先把通用原理讲清楚（FLOPs 怎么数、attention 什么时候不能忽略、精度体系、算力峰值、MFU），
H3 的数字只在"验证/反例"的位置出现，**不作为标题主语，不作为开场钩子**。真正的主线是四块拼图：

1. 要算多少次浮点运算（FLOPs 估算）
2. 用什么数据格式算（精度体系）
3. 机器一秒能算多少（算力峰值）
4. 实际能拿到多少（MFU）

每讲完一个通用公式，才追问一句「这个公式对视频 DiT（以 H3 为例）还成立吗」——这是**验证环节**，不是章节的存在理由。

## 记法与假设（贯穿全章）

- 对照锚点：**经典 LLM**（hidden=4096，常见对话上下文 s=4K），是全章公式的默认基准，出现顺序始终在 H3 之前。
- 例子模型 **MiniMax H3**（视频 DiT）只在需要验证"公式在非 LLM 架构上是否还成立"时出现，规格以一个紧凑的参考面板呈现，不单独占一屏：H3-Omni-Transformer 33B dense / 50 层 / hidden 5376 / 56 heads；AdaLN 分支 ≈13B 可预计算缓存 → **计算路径有效参数 N_eff ≈ 20B**；VAE 空间16×/时间4×压缩，patchify 后等效空间32×/时间4×；输出 24fps 原生2K、最长15秒、同步立体声。
- **待核实项**（不遮盖，小字标注）：vLLM 部署文档写 52 个 block（BF16 66.3GB），大纲用 50 层，定稿前需拉 `config.json` 校准；FFN 扩张比、head_dim 按标准 Transformer 假设推导。

## 章节内容（单页，按小节堆叠）

### 0. 本章任务

**要点：**
- 开篇问题链，四块拼图（见上），用一句话点出写作纪律：LLM 推理基础设施的两条公理——「decode 是访存受限的」「attention 的 s² 项可以忽略」——不是普适真理，本章要讲清楚它们**在什么条件下**成立、什么时候失效，用 H3 作反例验证，而不是先入为主地讲 H3。
- 例子模型参考面板（紧凑 `.panel`，非整屏表格）：MiniMax H3 关键数字一行放完，标注"本章验证用例，非主角"。

### 1.1 一切都是矩阵乘

**要点：**
- 公式：`[m,k]×[k,n] 的 GEMM = 2mkn FLOPs`。核心概念：Transformer 里 95%+ 的浮点运算集中在少数几个 GEMM 上，「数 FLOPs」≈「数矩阵乘」——这对任何 Transformer 变体（LLM、DiT）都成立，是通用起点。
- 验证：H3 单 block 的 FLOPs 分布图，指出 AdaLN 占 40% 参数却几乎不占 FLOPs（因为按 timestep 而非 token 计算）——用来说明"数参数量 ≠ 数 FLOPs"这个通用陷阱在 DiT 上更容易踩。

### 1.2 前向 2N，以及"N 到底是多少"

**要点：**
- 通用公式：`每 token 前向 ≈ 2N FLOPs`，每个权重恰好参与一次乘加。这条公式对任何 dense Transformer 都成立，先讲清楚原理和推导。
- 验证：套到 H3 上时 N 不是 33B 而是 N_eff≈20B（AdaLN 不参与逐 token 计算），当场用架构参数反推验证（50层×12×5376²≈17.3B，量级吻合）。
- 通用概念：token 数由分辨率/时长/帧率/压缩率决定，对图像和视频类模型这是平方项 × 线性项的组合，用 H3 的四个配置（1344×768/5s→2K/15s，30,240→324,000 token）做量级示范，而非目的本身。
- 附带一句通用观察：多模态（音频轨）在 token 预算里的占比通常远小于视觉轨——这是设计多模态系统时的通用直觉，H3 的 0.4% 只是一个例证。

### 1.3 训练的 6ND

**要点：**
- 通用公式：`C≈6ND`，反向是前向两倍的原因（dX+dW 各一次同规模 GEMM）——对任何 Transformer 训练都成立。
- 验证：DiT 训练侧的两个例外要点（AdaLN 训练时要算梯度、扩散训练不乘步数），用 H3 做例子，但先说清楚这是"扩散模型这一类架构"的共性，不是 H3 独有。

### 1.4 Attention 的 s² 项：什么时候不能再忽略

**要点：**
- 通用公式：`attention/linear ≈ s/(6h)`——这是全章最重要的一个判据，适用于任何 Transformer：序列长度 s 相对 hidden h 越大，attention 占比越高。
- 通用结论先行：LLM 场景 s 通常远小于 6h，所以"attention 可忽略"是一个**在特定 s/h 区间下成立的经验规则**，不是公理。
- 用五个场景的对照表（LLM 对话 0.17 → H3 2K/15s 10.0）做验证——H3 只是用来证明"这个区间可以被轻易突破"的一个例子，任何长序列场景（长文档、长视频、长音频）都可能落入同样的区间。
- 一句话收敛这一节的落点：**不是"DiT 需要不同的公式"，而是"同一个公式，token 数一旦跨过 6h 这个尺度，结论就会反转"**——这是可迁移到任何长序列系统的判断方法。

### 1.5 扩散模型推理的计算结构（补充公式，非 LLM 专属对比）

**要点：**
- 明确定位：这是 LLM 材料里没有的一类计算结构——不是"DiT 特有"，而是**扩散/迭代式生成模型**这一类方法共有的结构：`推理 FLOPs ≈ steps × cfg × (2·N_eff·s + 4·L·s²·h) + 解码 + 编码`。
- 用 H3 数字走一遍单步→端到端（2.2 PFLOPs/步 → 220 PFLOPs → 9分钟/5秒视频），目的是让"steps × cfg 是一个独立于 token 数之外的乘子"这个通用概念有具体手感，不是记住 220 这个数字本身。
- 通用杠杆表（步数蒸馏、CFG 简化）说明：任何迭代式生成模型的优化空间主要在"减少迭代次数"，这一条经验可迁移到扩散图像生成、扩散语言模型等其他场景，H3 只是当前案例。

### 1.6 流式推理与 LLM decode 的本质差异

**要点：**
- 核心通用判据（全章最重要的对照表）：LLM decode 每步 1 token、算术强度低、访存受限；分块自回归的迭代式生成模型每步一个 chunk（token 数远大于 1）、算术强度高 2–3 个数量级、仍是计算受限。这是可迁移的判据：**任何"每步处理的 token 数"远大于 1 的自回归系统，都不能直接套用 LLM decode 的优化经验**（continuous batching、投机解码、权重量化优先）。
- 用 H3 的 chunk 数字（6,048 token/chunk，5秒时开销涨5倍）做具体验证，同时明确标注 H3 本身不是流式模型，这里讨论的是"假设做分块自回归会怎样"的推演，避免读者误以为在描述 H3 的真实部署形态。

### 1.7 精度体系

**要点：**
- 通用内容，和具体模型架构无关：FP32/TF32/FP16/BF16/FP8/FP4 位域对比、BF16 为什么是训练默认（精度换动态范围，不需要 loss scaling）、混合精度三件套、FP8 scaling 的必要性。
- 唯一的验证性补充：迭代式生成模型（含扩散）的误差会沿"步数"串联累积，这是和 LLM 单次前向不同的通用结构性差异（不只 H3 如此），量化容忍度要按最终输出质量评估。分模块精度策略表里 AdaLN 缓存那一行标注"H3 具体实现，供参考"。

### 1.8 算力峰值：读懂 spec sheet

**要点：**
- 完全通用的内容：峰值公式、代际峰值对比（A100/H100/H200/B200）、三个坑（稀疏峰值×2、TF32 走 Tensor Core、标称频率≠实际频率）、H100≈1PFLOPS BF16 的锚点数字。这一节不需要 H3 出场。
- 唯一提及 H3 的地方：显存与算力配比的选择在"计算密集型架构"（如 DiT）和"访存密集型场景"（如 LLM decode）上导向不同的硬件选型，用 H3 的显存数字（66.3GB）做一句话例证，不展开。

### 1.9 MFU：从峰值到现实

**要点：**
- 通用公式与典型区间（LLM 训练 35–50%、LLM decode <5%）完全独立于 H3。
- 双栏 MFU 瀑布图：左栏 LLM decode、右栏"计算受限的迭代式生成系统"（以 H3 的量级为参考，不专指 H3），说明两类系统的优化重心分岔——这张图是全章方法论的总结，H3 只是给右栏提供一个可信的数量级参照。
- 实时性预算推演：给定目标帧率反推可行组合，用 H3 的数字走一遍（9分钟→22秒→逼近实时），作为"如何用本章四块拼图做工程决策"的示范流程，可迁移到任何模型。

### 1.10 速查卡与过渡

**要点：**
- 双栏对照速查卡（LLM vs 迭代式/长序列生成系统的通用判据），H3 的具体数字不再出现，只留公式和结论，保证这张收尾卡片是可迁移的方法论工具，不是 H3 专属总结。
- 过渡钩子：「既然一直是计算受限，第二章的访存分析还有意义吗？」→ 有，VAE 解码/norm/流式历史 KV 是访存侧大头。
