① 性能估计

显存去哪了，快不快：三项分解 + Roofline

显存三项分解：权重 / 激活 / KV cache

任意时刻的显存占用都可以拆成三项，此消彼长：训练时权重与激活主导，推理解码时权重与 KV cache 主导。 下面三节会把同一套公式套在经典 LLM、MAGI、LTX-2 三个真实形状上。

权重 Weights

参数量 × 精度字节数，训练时再加优化器状态/梯度。

激活 Activations

batch × seq × hidden × layers；是否开重计算差一个数量级（细节留给⑤）。

KV cache

2 × layers × heads × head_dim × token 数 × batch × bytes（K、V 各一份，故×2）。

走一遍：Llama-2-7B 级配置

hidden=4096, layers=32, heads=32, head_dim=128，参数量 6.7B。

120.6 GB 训练权重+优化器（bf16权重13.4 + fp32主权重26.8 + 梯度26.8 + Adam动量53.6），单卡放不下——④会用ZeRO/FSDP解决
97 → 2 GB 训练激活（batch=1, seq=4096）：不开重计算 97GB，开满重计算 2GB——⑤展开机制
2.0 → 64 GB 解码 KV cache：单请求 seq=4096 时 2GB，32 个并发占满上下文时 64GB——服务吞吐的隐形天花板

三项里权重相对固定，激活和 KV cache 才是随配置暴涨的部分。

落到 MAGI：更大的 hidden，垒得更快

hidden=5120, layers=40, head_dim=128（heads=40）。参数量按 dense block 估算 12·h²·L ≈ 12.6B （近似估算，MAGI 未公开精确参数量，仅用于量级对比）。

23.4 GB bf16 权重（推理 / SFT-DMD 蒸馏后常见形态）
151.6 GB 激活（假设单步 4096 个 latent token，batch=1，不开重计算）——同公式，hidden 和 layers 都更大，涨得比经典 LLM 更快
3.125 GB 流式生成 KV（frame-reservoir + eviction，见 SNL 机制）：缓存只保留 reservoir 深度内的窗口，大小不随生成总长度增长

换成视频 DiT 形状，公式不变，但每一项的账单都变了——尤其是 KV 从"随 seq 线性增长"变成"恒定窗口"。

落到 LTX-2：sink + 滑窗，显存有硬上限

LTX-2 仅 layers=48 是公开规格；本节 hidden=4096 为示例参数（非产品真实值），只用于展示 sink+滑窗 KV 策略的形状。

6.0 GB 2×48×32×128×8192×2 bytes——硬上限，生成再长的视频也不会突破
文本交叉注意力 K/V

依赖当前噪声级 sigma，不缓存、每步重算——用算力换掉了存储，呼应下一节的 roofline。

Roofline 直觉：省显存还是省带宽

实际吞吐 = min(峰值算力, 带宽 × 算术强度)；算术强度 AI = FLOPs / 搬运字节数， AI 越低越"带宽受限"，越高越"算力受限"。

显存三项分解告诉你"占多少"，roofline 告诉你"快不快"——两者合起来是①的完整答案， ② 通讯的代价模型会在此基础上继续展开。

② 通讯原语

五种通讯原语 + α-β 代价模型

五原语：谁在搬什么

后面③④两章的并行方案，本质上都是"用哪种原语搬多少数据"。先建立统一直觉，再挂公式。

all-reduce

每卡一份数据，规约后每卡都拿到相同的完整结果。

all-gather

每卡一片数据，不规约，每卡拿到所有分片拼起来的集合。

reduce-scatter

每卡完整数据，规约后每卡只留自己那一片，结果分散不重复。

all-to-all

每卡给每张卡发不同的一小片（转置式交换），常见于路由类操作。

p2p (point-to-point)

只在两张卡之间单向/双向传一份数据，无广播无规约。

all-reduce/all-gather/reduce-scatter 常成对出现在参数/梯度分片场景，all-to-all 用于路由，p2p 用于流水线相邻阶段——④会逐一对号入座。

α-β 代价模型：朴素做法 vs Ring

单次点对点传输 T = α + β·M：α 是每条消息的固定延迟（消息越小越吃亏）， β=1/带宽 是搬运成本（消息越大越吃这个）。硬件量级：节点内 NVLink 300 GB/s（α≈5μs）， 跨节点 200Gbps InfiniBand 仅 25 GB/s——约为 NVLink 的 1/12，④讲多机训练时拓扑感知的伏笔。

以①的经典 LLM 梯度（bf16 13.4 GB）在 P=8 卡 NVLink 环上做 all-reduce 为例：

625 ms 朴素做法（单卡收集再广播）：瓶颈卡收 7 份、发 7 份 = 2×7×13.4GB / 300GB/s，且随 P 线性变差
78 ms Ring all-reduce：每卡只搬 2×(8-1)/8×13.4GB ≈ 23.45GB，耗时 23.45GB / 300GB/s——快 8×

ring 算法把"单点瓶颈"摊成"环上均摊"：每卡数据量随 P 增大趋于常数 2M，代价从 O(P) 降到 O(1)（单卡视角）。

Ring All-Reduce 分步动画：reduce-scatter 半环 + all-gather 半环

8 卡排成环。阶段一 reduce-scatter（7 步）：每步把一个分片发给右邻居并累加，7 步后每卡恰好持有一个"完全规约好"的分片。 阶段二 all-gather（7 步）：把已规约的分片继续沿环转发（不再累加），7 步后每卡集齐全部分片。共 2(P-1)=14 步， 每步每卡收发一个大小 M/P 的分片——正是上一节 78ms 数字背后的真实数据流。

五原语代价对比：谁在④出场

原语 每卡数据量（最优实现） 延迟敏感度 ④出场
all-reduce 2(P-1)/P·M 中（消息大时 β 主导） TP 每层前向/反向同步激活
all-gather (P-1)/P·M 中 DP/ZeRO 收集分片参数
reduce-scatter (P-1)/P·M 中 DP/ZeRO 规约并分片梯度
all-to-all (P-1)/P·M，常配小消息 高（α 常主导） EP 路由 token 到专家卡
p2p M（单次） 低（大消息时） PP 相邻 stage 传激活
35 μs all-to-all 例（MoE 路由，每卡给其余 7 卡各发 2MB）：7×5μs(α项) + (7/8×16MB)/300GB/s(β项≈0.05μs)——消息越碎，α 越主导，是 EP 章要优化的根源
0.34 ms p2p 例（PP 传 100MB 激活）：5μs + 100MB/300GB/s——远小于 all-reduce，因为只发一份不做规约/收集

五种原语的代价差异，本质是"消息大小 vs 消息数量"在 α/β 两项之间的取舍——这套语言会在③④两章反复复用。

③ 序列并行

长视频 token 序列怎么切：Context Parallelism

为什么要切序列：CP 切的维度和 TP 不一样

①已展示 seq=4096 时单层激活就有 3 GB 量级；离线/非流式长视频序列可达 131072（128K）token（区别于①③MAGI streaming 用的 4096-token 单 chunk），激活线性暴涨，单卡装不下同一批次的完整序列。

三种 CP 方案的共同问题：Q 在本地就能算，但 attention 需要全部 K/V 才能算对——如何跨卡拿到全部 K/V，是分歧点。

Ulysses：all-to-all 换轴

平时按"序列切分、头全量"存 Q/K/V；attention 计算前做一次 all-to-all，换成"序列全量、头切分"（每卡拿到全部 token 但只算一部分 head），算完再换回去。

0.93 ms/层 P=8，每卡 QKV 张量 16384×5120×2bytes≈160MB，all-to-all 移动 (P-1)/P×160MB=140MB，耗时 140MB/300GB/s≈0.47ms；前后各一次（QKV 换轴+输出 O 换回）
硬约束

并行度 P 不能超过头数（MAGI heads=40），是它相对 Ring 的限制。

Ring-Attention：KV 沿环流转

每卡固定持有一段 Q，K/V 分片像②的 ring all-reduce 一样沿环逐步传递（p2p，P-1 步），每收到一个新分片就和本地 Q 做局部 attention 并累加 online softmax 统计量，不需要等全部 K/V 到齐。

7.47 ms/层 P=8，每步 K+V 分片 2×16384×40×128×2bytes≈320MB，耗时≈1.07ms；P-1=7 步——原始通讯量，实际可与计算重叠，暴露墙钟时间通常远小于此
优势

不受头数限制，纯按 token 数切，P 可以很大——对超长序列更常见。

MagiAttention / flex-flash-attn：给 Ring 加灵活掩码与负载均衡

建立在 FlashAttention-3 kernel 之上（tiling/IO-aware，⑤展开细节），核心新增两点： AttnSlice 广义掩码——能表达 MAGI 的 block-causal + 多模态掩码等异构 mask，并让不规则掩码仍可按 chunk 分布式切分； chunk 级负载均衡 + 零冗余通讯重叠——像 Ring-Attention 一样沿环传 KV，但对被掩码整块跳过的区域不计算也不搬运。

定性结论（不给虚构精确基准数字）：对 MAGI 这种带 block-causal 结构化稀疏掩码的场景，FFA 的有效通讯量低于上一节朴素 Ring 的 7.47ms/层估算，因为掩码外的分片直接跳过；具体加速比取决于掩码稀疏度，未公开可复算的基准数字，仅作定性说明。这是 MAGI 真实使用的方案。

三方案对比小结

方案 切分依据 通讯原语 并行度上限 本章数字
Ulysses 序列↔头 反复换轴 all-to-all ×2/层 受限于头数（≤40） 0.93 ms/层
Ring-Attention 固定按序列切，KV 环传 p2p ×(P-1)/层 不受头数限制 7.47 ms/层（原始，可重叠）

④ 训练并行范式

DP/ZeRO · TP · PP · EP：切什么，花多少

DP 的问题：单卡装不下 + ZeRO/FSDP 怎么解决

朴素数据并行 (DP)：每卡存完整模型+优化器状态，仅切分 batch； ①已算出 7B 训练权重+优化器 = 120.6 GB，单张 80GB 卡放不下——DP 单独用不了。

落到 Philoflow：16-GPU FSDP 训练 MAGI 级模型

Philoflow 用 accelerate + FSDP(=ZeRO-3)，P=16 卡训练 MAGI 级（12.6B）模型。

210.6 GB 训练总显存占用（AdamW混合精度，按①7B同比例 120.6/13.4≈9× 估算）：bf16权重23.4GB × 9
13.2 GB/卡 FSDP-3 分到 16 卡后：210.6GB / 16——单卡轻松放下，且留有余量给激活

为什么不用 TP/PP：MAGI 级模型（12.6B）远小于需要 TP/PP 的百亿级+ LLM，FSDP 分片已把单卡显存压到 <20GB； 引入 TP 要承受每层同步 all-reduce 的延迟（下节），引入 PP 要承受流水线气泡（下下节）——在当前模型规模和 16 卡单集群规模下，两者的复杂度收益比不划算，Philoflow 选择只用 FSDP 扩展。

TP（张量并行）：切开单层权重矩阵

Megatron 式 TP：把单层权重矩阵（QKV、MLP）按列/行切到多卡，每卡算一部分，层末用 all-reduce 合并结果——用②的 all-reduce 公式，但发生在每一层内部。

0.39 ms/层 经典LLM，TP=8：单层消息 4096×4096×2bytes≈33.6MB，all-reduce 2×(8-1)/8×33.6MB/300GB/s≈0.196ms，attn+MLP各一次
12.6 ms/step 32 层累加；all-reduce 同步阻塞、延迟极敏感，几乎只用节点内 NVLink——Slide2 中 Philoflow 放弃 TP 的另一理由

PP（流水线并行）：切开层，代价是气泡而非带宽

把模型按层切成多个 stage，跨卡分布；stage 间只需 p2p 传激活/梯度（②公式，代价很低）。核心代价不是通讯量，而是流水线气泡 (bubble)： P 个 stage、M 个 micro-batch 时，气泡占比 ≈ (P-1)/(P-1+M)。

27.3 % P=4 stage，M=8 micro-batch：气泡 = (4-1)/(4-1+8) = 3/11
15.8 % M 增到 16：气泡降到 3/19——micro-batch 越多气泡越薄，但需缓存更多 in-flight 激活

EP（专家并行）：token-routed 才能 EP，modality-experts 不行

MoE 层每卡常驻若干专家的全部权重，router 给每个 token 动态选 top-k 专家，token 需经 all-to-all（②公式）跨卡送到专家所在卡，算完再送回——这是 token-routed experts。

35 μs 直接复用②Slide4 的路由数字：8 卡、每卡给其余 7 卡各发 2MB 分片，α 项主导——EP 的通讯瓶颈本质就是②讲过的"消息碎、α 项吃紧"
MAGI modality-experts 为何不需要 EP

num_modality=3：不是 router 学出来的动态选择，而是按模态（video/text/…）静态决定用哪套投影，同一模态的 token 永远走同一分支——不需要跨卡动态路由，也就不需要 all-to-all。

一句话区分：EP 解决"动态路由到哪张卡"的通讯问题，只对 token-routed experts 有意义；MAGI 的 modality-experts 是静态分派，压根不产生 EP 要解决的那种通讯模式。

⑤ 显存与计算优化

兑现前面的钩子：重计算 · 混合精度 · Offload · FlashAttention · KV Cache

激活重计算 (activation checkpointing)：97GB → 2GB 怎么来的

反向传播需要前向的中间激活；不重计算时全部保留 = O(层数)×每层激活。重计算只保留层边界的少量张量，反向时重新跑一遍前向补出被丢弃的中间激活，用算力换显存。

97 → 2 GB 兑现①的钩子：经典 LLM 7B，seq=4096，不开重计算单层3.03GB×32层≈97GB；开满重计算单层0.06GB×32≈2GB——只保留层边界输入
+33 % 额外计算量：1次前向+1次反向(≈2倍前向算力)=3份，加一次重算前向=4份，4/3-1≈33%

这是"存 vs 算"权衡的第一个具体例子，呼应①的 roofline 收口。

混合精度：120.6GB 分解里每一项在干嘛

为什么用 bf16 而不是 fp16：bf16 指数位与 fp32 相同（8 位），动态范围一致，不需要 loss scaling； fp16 指数位只有 5 位，训练大模型容易下溢，需要额外的 loss-scaling 机制。

Offload：显存换 PCIe 带宽

把不在计算关键路径上的状态（典型是优化器状态）挪到 CPU 内存，用时再搬回 GPU——①roofline "存 vs 算"权衡的另一种形式："存 vs 搬运带宽"。

25 GB/s PCIe4 x16 带宽，远低于②NVLink 300GB/s（约 1/12）
2.14 s 7B模型Adam优化器状态53.6GB整体搬到CPU：53.6GB/25GB/s——比②③④任何一次通讯都慢一个数量级

因此 offload 只对"能和计算重叠、非关键路径"的状态划算（如优化器 step 与下一步前向重叠），不能天真地每步同步搬运。

FlashAttention 基础：tiling + IO-aware，不物化 N×N

FlashAttention 省的不是 FLOPs（数学上等价），是 HBM 读写次数——又一次"用什么带宽做什么事"的 roofline 式思考。

MagiAttention / flex-flash-attn：FA 的分布式 + 灵活掩码扩展

建立在上一节 FA-3 kernel 之上，③已讲过它在通讯维度的表现（chunk 级负载均衡+零冗余重叠，跳过掩码外分片）； 本节收口它在 kernel/掩码 维度的贡献：AttnSlice 广义掩码让 block-causal、多模态等异构掩码也能享受 tiling/IO-aware 的好处，而不必退化成朴素稠密 attention。

一句话：③讲的是"分布式怎么切"，本节讲的是"单卡 kernel 怎么快"，两者叠加才是 MAGI 实际训练/推理用的完整方案。

KV Cache 收口：Philoflow SNL 流式 + LTX-2 vs minimax h3

SNL (Same-Noise-Level)：MAGI self-forcing DMD 自回归生成的 KV-cache 噪声机制——上下文与当前去噪 chunk 处于同一噪声级，用 block-causal 掩码，每个噪声级一份 KV-cache； streaming 模式逐 chunk 生成、配 first-block/first-latent sink，实现无限长生成。兑现①的 3.125GB reservoir 数字：这就是 SNL 机制下的窗口大小。

模型 KV 策略 KV 大小 随生成长度
经典 LLM 逐 token 全量缓存 ①：2GB（单请求） 线性无界增长
MAGI SNL 同噪声级 + reservoir ①：3.125 GB 恒定窗口
LTX-2 sink + 滑动窗口，文本交叉注意力K/V不缓存(依赖sigma) ①：6.0 GB 恒定，硬上限
minimax h3 公开信息未描述明确的 AR 式 KV-cache 流式机制——推断边界：若推理管线含类似缓存/流式扩展，会面临同样的"缓存窗口 vs 生成长度"权衡，但具体数字未公开、无法复算，本行仅作定性类比

四者是同一问题在不同架构假设下的不同取舍：经典 LLM 线性无界增长 → MAGI SNL 窗口恒定 → LTX-2 sink+滑窗恒定且部分K/V不存 → minimax h3 策略未公开。

minimax h3（Hailuo 3.0）是本场 EP 的落点（④，token-routed MoE，35μs 路由通讯）+ KV cache 推断边界讨论（⑤，未公开明确 AR 式缓存机制的定性类比）。

35 μs EP 路由通讯（复用④数字）：token 经 all-to-all 送到专家所在卡
流式生成的理论叠加

若做长视频流式生成，理论上要在 EP 路由通讯之上叠加类似 SNL/sink+滑窗（⑤）的缓存策略控制显存——具体实现未公开，仅重申这是同一套语言能覆盖的问题，不新增数字。

对比 Philoflow：minimax h3 用 EP（专家维度并行），Philoflow 用 FSDP（参数维度并行）—— 两个真实系统选择了不同的并行维度，因为瓶颈不同：h3 的瓶颈在专家计算的稀疏调度，Philoflow 的瓶颈在稠密参数量。
