01 · 1.2 计算

统一工作量口径：三类操作

FLOP 一次浮点运算 · FLOPs 一段计算的总运算数 · FLOP/s 硬件每秒能完成的运算数。全篇把一次乘加计为 2 FLOPs。

反向：口径不变

对 C = AW，反向既算权重梯度 dW = AᵀdC，也算输入梯度 dA = dCWᵀ，两次各约 2mkn —— 合计约 4mkn FLOPs。

容易漏掉的部分

Reduction 的反向通常是广播或路由梯度，算术运算可能少于前向，但数据读写仍然存在。把反向实际执行的运算按同一口径计入，而不是乘一个固定系数。

01 · 1.2 参数量近似

用参数量反推计算量：2P → 6P → 6PD

起点仍是 GEMM：一次前向中，每个 token 对本次执行所用的矩阵权重大约做一次乘加。把实际参与计算的权重记为「有效参数量 P」。

核心结论

这只是假设

01 · 1.3 时间边界

两个下界，取较慢的一侧

实际时间通常更长
  • shape 太小或维度不友好，无法充分使用计算单元
  • 实际 HBM 读写多于「一次读、一次写」的最小逻辑量
  • 算子之间存在依赖、同步和空隙；kernel 启动、框架调度与数据准备有固定开销
  • 多设备时通信暴露在关键路径上
经验修正的边界

粗略时间 ≈ 理论下界 / 实测利用系数。但「相似」至少要包含硬件、精度、shape、kernel 路径和并行布局 —— 不存在可跨工作负载套用的通用利用率常数。

01 · 1.3 容量

峰值显存 = 同时存活，不是机械相加

单项公式很简单：张量容量 = num_elements × bytes_per_element。难的是判断哪些张量在同一时刻还活着。

长期驻留

跨越大部分执行过程 · 权重、常量表

阶段性状态

跨越一段逻辑阶段后可释放 · 输入、需保留的中间状态

临时空间

为某算子或通信短暂存在 · workspace、通信 buffer

两本 bytes 账的边界

一份权重占多少 HBM 是容量问题；执行期间从 HBM 读了几遍是数据移动问题。

三个容易混淆的 batch 口径

「跑不快」也要带口径

step time 衡量一次 optimizer update 的墙钟时间；samples/s、tokens/s 衡量单位时间的有效数据量。global batch 改了，单比 step time 会误导。

MFU 与 HFU

MFU 通常把实测有效模型计算量与硬件理论峰值比较；HFU 还可能把重计算等实际硬件工作计入分子。定义不统一时，只比较同一实现、同一口径的结果。

02 · 2.2 单卡

三类配置改变的是同一份账本

目标 global batch 不变、单卡执行四个 micro-step。它们不是三个互不相关的技巧。

混合精度 ≠ 全部改低精度

训练中可能同时存在低精度计算副本、较高精度更新状态和不同精度的归约。验证对象是峰值显存、step time 与训练质量，不是配置名。

先检查输入形状

大量 padding 会让 GPU 对无效 token 做真实计算；packing 提高有效 token 比例但改变样本边界；数据加载不及时则让 GPU 等待。这些都表现为利用率低，但不该用「加卡」解决。

02 · 2.6 PP

PP：切层之后，问题变成调度

4 个 stage、8 个 micro-batch，forward 与 backward 各算 1 个时间单位。两者总时长相同，差别在同时存活的激活数量。

GPipe

规则直观，但 backward 开始前保留更多在途 micro-batch 激活（峰值 ≈ micro-batch 数）。

1F1B

稳定阶段交替 forward 与 backward，峰值降到 ≈ stage 数。两者都无法消除预热与排空。

PP 的三项代价

若瓶颈是最多 511 次串行增量 decode，单个 kernel 快 5% 不会变成 5 倍端到端加速；减少小中间张量也不会改写权重搬运下界。

各自的适用条件

融合/编译：热点 shape 稳定、kernel 成熟，且观测到开销确在关键路径。投机解码：目标模型单步昂贵、接受率足够高、验证可有效并行；验证需报告平均接受 token 数、drafter 开销、TPOT 与质量。

03 · 3.4 状态池

KV cache 从连续预留变成状态池

prefix reuse

命中后 C 复用对应 KV，只处理自己的 suffix。要求模型执行上下文和 token 序列兼容；收益取决于前缀长度、命中率、驻留和淘汰。低命中率时，冷前缀反而挤占活动 KV。

paged KV 的边界

它不减少有效 token 的逻辑 KV，且有元数据、末块和专用 kernel 成本。收益必须落到稳定并发、OOM/碎片、吞吐或尾延迟上。

03 · 3.5 部署

多一张卡：增加副本，还是切分模型？

选择顺序

放得下且单请求已达标 → 先比较 replicas；放不下 → 先比较量化，仍不够再用 TP/PP；只有计算或 HBM 下界确实主导单请求时，才把 TP 当作降时延候选。

怎么判断切分是否值得

把每卡节省的权重/FLOPs、聚合带宽和可能分片的 KV，与新增 collective、同步、buffer 对照，再看 TTFT/TPOT、每卡吞吐和稳定并发。通信让 P99 变差，不能因「用了更多卡」视为优化。

03 · 3.6 验证

同时报告速度、容量、质量与成本

在 BF16、低并发 decode 中，实测单步时间远高于 FLOPs 下界并接近权重与 KV 搬运下界；只改变权重格式，验证权重 bytes、峰值显存、TPOT 和质量。
单请求基准

固定：模型版本、采样配置、输入长度分布、输出上限、精度、硬件、卡数、并行度；质量边界与测试集；warmup、重复次数、是否包含排队/编译。

报告：TTFT、TPOT、ITL 分布、端到端时延、峰值显存、任务质量、P50/P95/P99。

服务基准

固定：请求到达过程、输入/输出联合分布、并发或请求率、SLO、调度配置、副本数与每副本卡数、batch/token 上限、KV pool 配置。

报告：queue time、TTFT、ITL/TPOT、端到端 P95/P99、tokens/s、requests/s、最大稳定并发、KV block 占用、超时/OOM/拒绝率、GPU-hours 与单位成本。

顺序读结果时依次检查
1速度是否改善目标指标：吞吐提高但 P99 超出 SLO，不是在线目标下的成功
2容量是否真的可用：显存下降后，batch、活动 token 或稳定并发是否提高
3质量边界是否保持：量化、近似采样、步数、窗口和输出上限是否改变
4复杂度与稳定性是否可接受：编译回退、cache miss、碎片、抖动和故障恢复是否恶化
5成本是否改善：看整个服务的设备时和达标请求，而不是只看单卡峰值 token/s

停止条件也应预先写清：目标 SLO 已满足且继续优化不降低单位成本；容量已有安全余量；或下一项收益不足以覆盖质量风险和系统复杂度。没有停止条件的「继续榨利用率」很容易用用户延迟换取无效吞吐。
