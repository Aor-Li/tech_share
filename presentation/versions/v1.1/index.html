01 · 1.2 计算

统一工作量口径：三类操作

FLOP 一次浮点运算 · FLOPs 一段计算的总运算数 · FLOP/s 硬件每秒能完成的运算数。全篇把一次乘加计为 2 FLOPs。

反向：口径不变

对 C = AW，反向既算权重梯度 dW = AᵀdC，也算输入梯度 dA = dCWᵀ，两次各约 2mkn —— 合计约 4mkn FLOPs。

容易漏掉的部分

Reduction 的反向通常是广播或路由梯度，算术运算可能少于前向，但数据读写仍然存在。把反向实际执行的运算按同一口径计入，而不是乘一个固定系数。

01 · 1.3 存储

先看数据离计算单元有多远

GPU 计算不是直接在一整块「显存」上完成的。数据从 HBM 进入 L2、再进入 shared memory 或 L1，最后到寄存器供指令使用。越靠近执行单元，容量越小、通常越快。

01 · 1.3 容量

峰值显存 = 同时存活，不是机械相加

单项公式很简单：张量容量 = num_elements × bytes_per_element。难的是判断哪些张量在同一时刻还活着。

长期驻留

跨越大部分执行过程 · 权重、常量表

阶段性状态

跨越一段逻辑阶段后可释放 · 输入、需保留的中间状态

临时空间

为某算子或通信短暂存在 · workspace、通信 buffer

两本 bytes 账的边界

一份权重占多少 HBM 是容量问题；执行期间从 HBM 读了几遍是数据移动问题。

01 · 1.4 物理路径

第一层：数据从哪条链路上走过去

「有多少张 GPU」还不够，还要知道它们如何连接。同样搬 1 GB，走哪条链路决定了它是 1 毫秒还是 20 毫秒的事。

数值为常见配置的规格上限量级（随代际与机型变化），不是持续可得的有效带宽：小消息受延迟主导，大消息还要扣掉协议开销、拓扑映射和与他人共享链路的竞争。估算时先定位这条路径上最窄的一段。

01 · 小结

本章要点：三本账的估算口径

1.1 三本账
  • 算得动吗 · 放得下吗 · 扩得开吗
  • 先确定问的是哪一本，再找方法
  • 量级估算用来排除不合理判断，实测用来确认真实关键路径
1.2 计算
  • GEMM、Attention、逐元素三类操作统一成 FLOPs 口径
  • 投影随序列线性增长，Attention 随序列二次增长
  • 用参数量反推：前向 2P、训练一步 6P、全程 C ≈ 6PD
1.3 显存与数据移动
  • 层级：寄存器 → shared / L1 → L2 → HBM，越远越慢也越大
  • Roofline：算术强度决定计算还是带宽先到顶
  • 峰值显存看同时存活的张量，不是各项机械相加
1.4 通信
  • 物理路径：HBM → NVLink → PCIe → 跨机 IB，带宽逐级下降
  • 通信元语：send/recv、带 root 的四个、全员参与的四个
  • 张量布局：复制 · 切分 · 分阶段，元语负责在布局之间转换

02 · ② 单卡 · 三条杠杆

单卡三条杠杆，改的是同一份账本

目标 global batch 不变、单卡执行四个 micro-step。混合精度、梯度累积、重计算不是三个互不相关的技巧，而是在同一张显存 / 时间账上换不同的项。

三条杠杆的分工

混合精度改每元素字节数与计算路径；梯度累积改单次 forward/backward 的形状；重计算改保存多少激活。下面三页各展开一条。

先检查输入形状

大量 padding 会让 GPU 对无效 token 做真实计算；packing 提高有效 token 比例但改变样本边界；数据加载不及时则让 GPU 等待。这些都表现为利用率低，但不该用「加卡」解决。

柱高为示意比例，用于比较改变的是哪一段content/02 · 2.2
02 · ② 单卡 · 混合精度

混合精度：按环节选精度，不是整份账本改低精度

混合精度 ≠ 全部改低精度

训练中可能同时存在低精度计算副本、较高精度更新状态和不同精度的归约。具体组合由算法与框架决定，要验证的是峰值显存、step time 与训练质量，不是配置名。

收益集中在激活与搬运

主权重与优化器状态通常仍按较高精度保存，所以状态那一段缩得有限。状态主导的 OOM 要靠状态分片解决，换精度顶不上去。

精度组合随框架与算法而异，图中为最常见的一种分工content/02 · 2.2
02 · ② 单卡 · 梯度累积

梯度累积：把一次更新拆成多个 micro-step

目标 global batch 不变，单次 forward/backward 的形状变小，激活峰值随之下降；代价是同一次更新要跑更多轮。

「跑不快」也要带口径

step time 衡量一次 optimizer update 的墙钟时间；samples/s、tokens/s 衡量单位时间的有效数据量。global batch 改了，单比 step time 会误导。

MFU 与 HFU

MFU 通常把实测有效模型计算量与硬件理论峰值比较；HFU 还可能把重计算等实际硬件工作计入分子。定义不统一时，只比较同一实现、同一口径的结果。

忽略最后一个不完整 batch；累积不减少总样本工作量，小 shape 还会重复支付固定开销content/02 · 2.1 / 2.2

02 · 小结

本章要点：训练的三段优化路径

① 流程与主要问题
  • 工作单元是一次参数更新，不是一次 forward
  • 显存峰值常出现在 forward 末尾，随激活变化
  • global batch = m × a × d，改一个量要说明另外两个是否固定
  • 三类问题：单卡放不下 · 单卡粒度不够或供给不足 · 多卡通信与等待抵消算力
② 单卡三条杠杆
  • 混合精度：低精度做计算与搬运，较高精度做更新与关键归约
  • 梯度累积：缩小单次 forward/backward 的形状，global batch 不变
  • 重计算：只保存检查点，backward 前重算，用计算换显存
  • 三者动的是同一份账本，不是三个互不相关的技巧
③ 多卡六类切分
  • batch → DP；训练状态 → ZeRO / FSDP；层内张量 → TP
  • 层 → PP；序列 / 上下文 → SP / CP；专家 → EP
  • 每类都回答四问：少持有什么 · 少算什么 · 要交换什么 · 代价是什么
  • 维度可以组合，但组合不会取消各自的代价

03 · 3.4 状态池

KV cache 从连续预留变成状态池

prefix reuse

命中后 C 复用对应 KV，只处理自己的 suffix。要求模型执行上下文和 token 序列兼容；收益取决于前缀长度、命中率、驻留和淘汰。低命中率时，冷前缀反而挤占活动 KV。

paged KV 的边界

它不减少有效 token 的逻辑 KV，且有元数据、末块和专用 kernel 成本。收益必须落到稳定并发、OOM/碎片、吞吐或尾延迟上。

03 · 3.5 部署

多一张卡：增加副本，还是切分模型？

选择顺序

放得下且单请求已达标 → 先比较 replicas；放不下 → 先比较量化，仍不够再用 TP/PP；只有计算或 HBM 下界确实主导单请求时，才把 TP 当作降时延候选。

怎么判断切分是否值得

把每卡节省的权重/FLOPs、聚合带宽和可能分片的 KV，与新增 collective、同步、buffer 对照，再看 TTFT/TPOT、每卡吞吐和稳定并发。通信让 P99 变差，不能因「用了更多卡」视为优化。

03 · 小结

本章要点：从单次执行到并发服务

3.1 目标与指标口径
  • 同一个 token/s 可能回答三个问题：在线交互 · 在线非流式 · 离线生成
  • 写清是 output tokens/s、input+output tokens/s 还是 requests/s，以及单卡还是整个服务
  • 稳定并发 = 给定到达分布与 SLO 下能持续服务的并发
3.2 prefill 与 decode
  • 一次 prefill 建立 KV，之后每步 decode 读已有 KV 并追加
  • prefill 位置可并行、易形成大矩阵；decode 步骤之间串行、单步粒度小
  • 两阶段落在 Roofline 的不同侧，主要影响 TTFT 与 TPOT
3.3 单请求提速
  • 量化：少搬少存；权重、激活与 KV 是不同账本项，质量必须验证
  • 融合与编译：热点 shape 稳定、开销确在关键路径时才有收益
  • 投机解码：用可并行的验证换串行等待，要报告接受率与 drafter 开销
3.4 并发服务
  • continuous batching：按迭代调度，完成的请求退出、新请求随时进入
  • KV 状态池：从连续预留改成按 block 分配，减少预留与碎片
  • 长 prefill 会挤占正在 decode 的请求；chunked prefill 是 TTFT 与 ITL 之间的取舍
3.5 多卡部署
  • 放得下且单请求已达标 → 先比较 replicas；放不下 → 先比较量化，仍不够再用 TP / PP
  • 只有计算或 HBM 下界确实主导单请求时，TP 才是降时延的候选
  • 通信让 P99 变差时，不能因为「用了更多卡」就算作优化
任何比较之前先固定工作负载、质量边界与目标指标content/03
